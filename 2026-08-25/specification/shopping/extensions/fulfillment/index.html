    풀필먼트 확장¶

    개요¶

    풀필먼트 확장을 사용하면 비즈니스가 배송, 픽업 같은 실물 상품 풀필먼트를 지원한다고 알릴 수 있습니다.

    이 확장은 체크아웃 및/또는 카탈로그에 fulfillment 필드를 추가합니다.

    • 체크아웃(dev.ucp.shopping.checkout) — 선택과 비용: 어떤 상품을 어디로, 어떤 방법으로, 얼마의 가격과 예상 도착 시간(ETA)으로 보낼지
    • 카탈로그(dev.ucp.shopping.catalog.search 및 dev.ucp.shopping.catalog.lookup) — 디스커버리: 제공된 구매자 컨텍스트를 바탕으로 각 변형(variant)에서 이용할 수 있는 풀필먼트 옵션을 알립니다. 카탈로그 디스커버리를 참고하세요.

    체크아웃의 fulfillment 필드에는 다음이 담깁니다.

    • methods[] — 장바구니 상품에 적용되는 풀필먼트 방법(배송, 픽업 등)
      • line_item_ids — 이 방법으로 풀필먼트할 상품
      • destinations[] — 풀필먼트할 장소(주소, 매장 위치)
      • groups[] — 비즈니스가 생성한 패키지. 패키지마다 선택할 수 있는 options[]가 있음
    • available_methods[] — 상품별 재고 가용성(선택 사항)

    멘탈 모델:

    • methods[0] 배송
      • line_item_ids 👕👖
      • selected_destination_id = destinations[0].id 🔘✅ 123 Fake St
      • groups[0] 📦👕👖
        • selected_option_id = options[0].id 🔘✅ 일반 배송 $5
        • options[1] 🔘 특급 배송 $10
    • methods[1] 매장 픽업
      • line_item_ids 👞
      • selected_destination_id = destinations[0].id 🔘✅ Uptown Store
      • groups[0] 📦👞
        • selected_option_id = options[0].id 🔘✅ 매장 내 픽업

    위치 컨텍스트¶

    기본 컨텍스트에는 선택 사항인 location이 정의되어 있습니다. 비즈니스 네임스페이스 안에서 안정적이고 불투명한 위치(Location) 식별자입니다. 이 필드는 카탈로그 요청과 장바구니 및 체크아웃 생성·수정 요청에 나타납니다(체크아웃 컨텍스트 참고). 풀필먼트 확장은 이 필드를 추가하거나 재정의하지 않고, 확장이 활성화되었을 때 이 필드가 어떤 효과를 내는지만 정의합니다.

    풀필먼트가 카탈로그나 체크아웃을 확장할 때, 해당 기능에 보내는 요청의 context.location은 잠정적인 비즈니스 위치를 가리킵니다. 비즈니스는 이 위치를 기준으로 풀필먼트 가용성을 평가하고 초기 풀필먼트 선택지를 만듭니다. 이 필드로 풀필먼트 목적지가 선택되지는 않습니다.

    다음 필드는 한 값의 정밀도 차이가 아니라 각기 다른 역할을 맡습니다.

    필드 역할
    context.location 풀필먼트를 평가하는 기준이 되는 잠정적 비즈니스 위치
    카탈로그 filters.fulfills_to 상품을 풀필먼트할 명시적 목적지이자 결과 필터
    카탈로그 methods[].location 변형의 장소 기반 방법(예: pickup)에 대해 확정된 비즈니스 위치
    체크아웃 methods[].selected_destination_id 해당 방법의 destinations[] 중에서 선택된 목적지

    우선순위는 각 필드가 관장하는 범위 안에서만 적용됩니다.

    • 카탈로그 filters.fulfills_to가 있으면 비즈니스는 풀필먼트 목적지와 방법의 availability를 context가 아니라 이 필드를 기준으로 반드시 확정해야 합니다(MUST). 다른 context 필드는 영향을 받지 않습니다.
    • 플랫폼이 체크아웃 방법에 selected_destination_id를 설정하면, 비즈니스는 그 방법의 풀필먼트 범위에서 context.location 대신 참조된 목적지를 반드시 사용해야 합니다(MUST). 다른 방법은 영향을 받지 않습니다.

    위치 이어 가기. 같은 식별자가 이 필드 중 여러 곳에 나타나더라도 역할이 서로 합쳐지지는 않습니다. 예를 들어 카탈로그 응답이 loc_123에서 이용할 수 있는 장소 기반 방법을 보고했다고 합시다. 기본 장바구니 컨텍스트에 이미 location이 있으므로 loc_123을 장바구니 요청의 context.location으로 이어 쓸 수 있습니다. 장바구니-체크아웃 전환에서는 장바구니의 context로 체크아웃을 초기화하므로, 비즈니스는 loc_123으로 초기 체크아웃 풀필먼트 목적지를 만들 수 있습니다(MAY). 플랫폼이 selected_destination_id를 설정하면 그 명시적 선택이 우선합니다.

    스키마¶

    풀필먼트는 물리적 배송이 필요한 상품에만 적용됩니다. 풀필먼트가 필요 없는 상품(예: 디지털 상품)은 방법에 할당하지 않아도 됩니다.

    풀필먼트¶

    이름 타입 필수 여부 설명
    methods Array[Fulfillment Method] 선택 장바구니 상품의 풀필먼트 방식.
    available_methods Array[Fulfillment Available Method] 선택 재고 가용성 힌트.

    풀필먼트 방법¶

    이름 타입 필수 여부 설명
    id string 필수 고유 풀필먼트 방식 식별자.
    type string 필수 풀필먼트 방식 유형. 잘 알려진 값: shipping, pickup. 비즈니스는 추가 값을 사용할 수 있습니다(MAY).
    line_item_ids Array[string] 필수 이 방식으로 풀필먼트되는 라인 아이템 ID.
    destinations Array[Fulfillment Destination] 선택 이 방법에 사용할 수 있는 목적지. 비즈니스 응답에서 각 목적지에는 type과 id가 있습니다.
    selected_destination_id ['string', 'null'] 선택 선택한 목적지의 ID. 비즈니스가 이 방식에 대해 인식하는 안정적인 비즈니스 범위 ID라면 무엇이든 받으며, 아직 destinations에 나열되지 않은 위치 ID도 포함합니다.
    groups Array[Fulfillment Group] 선택 옵션 선택을 위한 풀필먼트 그룹. 에이전트는 그룹에 selected_option_id를 설정해 배송 방식을 선택합니다.

    풀필먼트 목적지¶

    이름 타입 필수 여부 설명
    type string 필수 목적지 계약 판별자. 비즈니스 응답에서는 필수이고 플랫폼 요청에서는 선택입니다. 잘 알려진 값: shipping_address, business_location. 요청 기본값과 플랫폼이 쓸 수 있는 필드는 이를 감싸는 방식 계약이 정의하며, 협상된 확장이 추가 값을 정의합니다.
    id string 필수 풀필먼트 목적지 식별자.

    배송 목적지¶

    이름 타입 필수 여부 설명
    extended_address string 선택 아파트 호수, C/O, 대체 이름 같은 주소 보충 정보.
    street_address string 선택 도로명 주소.
    address_locality string 선택 도로명 주소가 속하고 해당 지역 안에 있는 시·군·구. 예: Mountain View.
    address_region string 선택 시·군·구가 속하고 해당 국가 안에 있는 지역. 해당하는 국가에서는 필수입니다(예: 미국의 주, 캐나다의 주). 예: California 또는 그 밖의 적절한 1차 행정 구역.
    address_country string 선택 국가. 2자리 ISO 3166-1 alpha-2 형식(예: "US")을 권장합니다. 하위 호환성을 위해 "SGP" 같은 3자리 ISO 3166-1 alpha-3 국가 코드나 "Singapore" 같은 전체 국가명도 사용할 수 있습니다.
    postal_code string 선택 우편번호. 예: 94043.
    first_name string 선택 선택 사항. 주소와 연결된 연락처의 이름.
    last_name string 선택 선택 사항. 주소와 연결된 연락처의 성.
    phone_number string 선택 선택 사항. 주소와 연결된 연락처의 전화번호.
    id string 필수 이 배송 목적지에 고유한 ID.
    type string 필수 상수 = shipping_address. 목적지 유형 판별자.

    비즈니스 위치 목적지¶

    이름 타입 필수 여부 설명
    id string 필수 비즈니스 범위의 안정적이고 불투명한 위치 식별자.
    name string 필수 구매자에게 표시되는, 비즈니스가 소유한 표시 이름.
    address Postal Address 선택 장소의 실제 주소.
    type string 필수 상수 = business_location. 목적지 유형 판별자. 응답 전용.

    위치 요약¶

    이름 타입 필수 여부 설명
    id string 필수 비즈니스 범위의 안정적이고 불투명한 위치 식별자.
    name string 필수 구매자에게 표시되는, 비즈니스가 소유한 표시 이름.
    address Postal Address 선택 장소의 실제 주소.

    풀필먼트 그룹¶

    이름 타입 필수 여부 설명
    id string 필수 업데이트 시 판매자가 생성한 그룹을 참조하기 위한 그룹 식별자.
    line_item_ids Array[string] 필수 이 그룹/패키지에 포함된 라인 아이템 ID.
    options Array[Fulfillment Option] 선택 이 그룹에 사용할 수 있는 풀필먼트 옵션.
    selected_option_id ['string', 'null'] 선택 이 그룹에서 선택한 풀필먼트 옵션의 ID.

    풀필먼트 옵션¶

    이름 타입 필수 여부 설명
    id string 필수 이 풀필먼트 옵션의 고유 식별자.
    title string 필수 형제 옵션과 이 옵션을 구분하는 짧은 레이블(예: 'Standard', 'Express Shipping', 'Curbside Pickup').
    description Description 선택 제목을 보충하는 맥락 정보(예: 'Arrives in 4 business days', 'Arrives Dec 12-15 via FedEx'). 그대로 렌더링할 수 있으며, 제목을 반복해서는 안 됩니다(MUST NOT).
    carrier string 선택 운송사 이름(배송용).
    earliest_fulfillment_time string 선택 가장 이른 풀필먼트 날짜.
    latest_fulfillment_time string 선택 가장 늦은 풀필먼트 날짜.
    totals Array[Total Response] 필수 풀필먼트 옵션 합계 내역.

    목적지¶

    풀필먼트 방법의 type은 상품을 어떻게 풀필먼트하는지(예: 배송 또는 픽업)를 나타내고, 목적지의 type은 풀필먼트가 어디서 이루어지는지(예: 배송 주소 또는 비즈니스 위치)를 나타냅니다. 두 구분자는 방향에 따라 역할이 다릅니다. 비즈니스 응답에서는 모든 목적지에 필수 type이 있으므로 응답만 보고도 내용을 알 수 있습니다. 플랫폼 요청에서는 방법의 계약이 destinations[]를 누가 작성할지 정하며, type을 생략했을 때 쓸 기본 목적지 형태를 정의할 수 있습니다(MAY).

    기본적으로 플랫폼은 방법의 destinations[]를 작성하지 않습니다. 다만 방법의 type별 계약에서 플랫폼이 작성할 수 있는 요청 형태를 선택적으로 허용할 수 있습니다(MAY).

    방법 type 요청 destinations[]
    shipping 플랫폼이 작성할 수 있습니다. 플랫폼이 구매자의 배송 주소 정보를 작성합니다.
    pickup 플랫폼이 작성할 수 없습니다. 비즈니스가 응답에 위치를 나열하고, 플랫폼은 비즈니스 범위의 ID로 위치를 선택합니다(선택과 위치 식별 참고).
    그 밖의 모든 방법 type 플랫폼이 작성할 수 없습니다(기본값). 비즈니스가 응답에 목적지를 나열하고, 플랫폼은 selected_destination_id로 하나를 선택합니다.

    목적지 type은 응답에서는 필수, 요청에서는 선택 사항입니다. 응답에서는 모든 목적지에 type이 있으므로, 목적지가 어디에 나타나든 그 자체로 의미가 분명합니다. 요청에서는 방법별 계약이 플랫폼 작성 형태를 허용하지 않는 한 destinations[]를 생략합니다.

    • 잘 알려진 shipping 방법에서는 모든 목적지가 배송 목적지입니다. type을 생략한 목적지는 기본값인 shipping_address로 간주합니다.
    • 잘 알려진 pickup 방법에서는 목적지가 응답 전용입니다. 플랫폼은 selected_destination_id로 위치를 선택합니다 (선택과 위치 식별 참고).
    • 그 밖의 방법 유형에는 기본값이 적용됩니다. destinations[]는 응답 전용이고, 응답의 각 목적지는 필수인 type과 id로 스스로를 설명하며, 플랫폼은 selected_destination_id로 하나를 선택합니다. 해당 방법을 정의하는 계약(이 명세의 향후 개정판이나 협상된 확장)에서 응답 목적지 형태를 좁히거나 플랫폼이 작성할 수 있는 요청 형태를 허용할 수 있습니다(MAY).

    destinations[]가 들어 있는 요청에는 방법의 type도 반드시 있어야 합니다(MUST). 잘 알려진 값은 다음과 같습니다.

    값 의미
    shipping_address 평탄한 우편 주소 필드로 이루어진 배송 목적지
    business_location 비즈니스 범위의 id로 식별하는 비즈니스 위치 목적지

    그 밖의 값은 협상된 확장에서 정의합니다. 그런 값에만 있는 목적지 필드는 해당 협상된 확장의 스키마로 검증합니다.

    선택과 위치 식별¶

    selected_destination_id는 방법 안에서 선택된 목적지를 id로 식별하며, 비즈니스 위치를 선택하는 유일한 수단입니다. 비즈니스가 해당 방법에서 인식하는 안정적인 비즈니스 범위 ID라면 무엇이든 받습니다. 비즈니스가 그 방법의 destinations[]에 (아직) 나열하지 않은 ID도 마찬가지입니다.

    선택은 ID의 출처를 따지지 않습니다. null이 아닌 selected_destination_id에는 플랫폼이 카탈로그 응답, 위치 검색이나 조회, 이전 체크아웃, 또는 비즈니스가 해당 방법에서 인식하는 그 밖의 출처에서 얻은 ID를 담을 수 있습니다(MAY). ID를 어디서 얻었든 아래 계약은 똑같이 적용됩니다.

    비즈니스가 null이 아닌 selected_destination_id를 수락하면, 그 응답은 다음 조건을 지켜야 합니다.

    • 방법에 같은 selected_destination_id 값을 반드시 담아야 합니다(MUST).
    • 같은 방법의 destinations[]에 id가 그 값과 같고 목적지에 명시된 대로 유형이 지정된 목적지를 정확히 하나 반드시 포함해야 합니다(MUST). 그래야 ID의 출처와 상관없이 응답만 보고도 내용을 알 수 있습니다.

    비즈니스는 선택된 목적지의 현재 가용성과 조건을 반드시 다시 검증해야 합니다(MUST). ID를 인식했다고 해서 재고가 확보되거나 자격이 보장되지는 않습니다. 비즈니스는 다른 목적지로 몰래 대체해서는 안 됩니다(MUST NOT). 다른 selected_destination_id를 반환해서도 안 되고(MUST NOT), 제출된 ID는 그대로 둔 채 다른 위치를 설명하는 목적지를 반환해서도 안 됩니다(MUST NOT). 제출된 선택을 이행할 수 없다면 비즈니스는 선택을 대체하지 말고 거부합니다.

    체크아웃 수정에서 제출된 selected_destination_id를 비즈니스가 수락할 수 없을 때(해당 방법에서 인식하지 못하는 ID이거나 재검증에 실패한 경우)는 수정 요청을 거부할 때의 일반 동작을 따릅니다. 즉, 현재 체크아웃을 반드시 변경하지 않은 채로 두어야 하며(MUST), severity: "recoverable"이고 path가 시도된 방법의 selected_destination_id를 가리키는(예: $.fulfillment.methods[0].selected_destination_id) 에러 메시지와 함께 그 체크아웃을 반드시 반환해야 합니다(MUST). 에러 처리와 path 필드를 참고하세요.

    렌더링¶

    풀필먼트 옵션은 방법에 구애받지 않는 렌더링(method-agnostic rendering)을 염두에 두고 설계되었습니다. 플랫폼은 특정 방법 유형(배송, 픽업 등)을 이해하지 못해도 옵션을 의미 있게 보여 줄 수 있습니다. 비즈니스가 미리 계산해 둔, 사람이 읽을 수 있는 필드를 제공하면 플랫폼은 이를 그대로 렌더링합니다.

    사람이 읽을 수 있는 필드¶

    위치 필드 필수 목적
    groups[].options[] title 예 형제 옵션과 구분되는 기본 레이블
    groups[].options[] description 아니요 제목을 보충하는 맥락 정보
    groups[].options[] totals 예 비용 내역: total 객체의 배열
    available_methods[] description 아니요 대체 가용성에 대한 독립적인 설명

    비즈니스의 책임¶

    options[].title의 경우:

    • 형제 옵션과 반드시 구분되어야 합니다(MUST).
    • 방법과 속도를 포함해야 합니다(SHOULD)(예: "Express Shipping", "Curbside Pickup").
    • description이 없어도 구매자가 결정을 내리기에 반드시 충분해야 합니다(MUST).

    options[].description의 경우:

    • title이나 total을 반복해서는 안 됩니다(MUST NOT). 보충 맥락만 제공합니다.
    • 배송 시점, 운송사, 그 밖에 결정에 필요한 세부 정보를 포함해야 합니다(SHOULD).
    • 완결된 구문이어야 합니다(SHOULD)(예: "Arrives Dec 12-15 via FedEx").
    • 제목만으로 의미가 분명하면 생략할 수 있습니다(MAY).

    available_methods[].description의 경우:

    • 무엇을, 언제, 어디서 이용할 수 있는지 설명하는 독립적인 문장이어야 합니다(MUST).
    • 플랫폼 대화에 그대로 쓸 수 있어야 합니다(SHOULD)(예: "Pants available for pickup at Downtown Store today at 2pm").

    정렬의 경우:

    • 비즈니스는 options[]를 의미 있는 순서(예: 저렴한 순, 빠른 순)로 반환해야 합니다(SHOULD).
    • 플랫폼은 그 순서를 유지해야 하지만(SHOULD), 알려진 구매자 선호도나 화면별 순위에 맞추려고 순서를 바꿀 수도 있습니다(MAY). 다만 방법/옵션 그룹 구조는 반드시 유지해야 합니다(MUST).

    플랫폼의 책임¶

    플랫폼은 풀필먼트를 범용적이고 렌더링 가능한 구조로 다뤄야 합니다(SHOULD).

    • 각 옵션을 title, description, total로 카드 형태로 렌더링합니다.
    • 반환된 방법을 모두 보여 줍니다. 어떤 방법을 고를지는 구매자가 결정합니다.
    • 방법과 옵션 구조를 그대로 유지합니다. 병합하거나 중복을 제거하지 않습니다. 정렬은 플랫폼이 정합니다.
    • available_methods[].description으로 구매자에게 대안을 보여 줍니다.

    플랫폼은 인식하는 방법 유형이라면 향상된 UX(픽업용 매장 선택기, 배송용 운송사 로고)를 제공할 수 있지만(MAY), 어디까지나 선택 사항입니다. 기본 계약은 title + description + total만으로 어떤 옵션이든 렌더링할 수 있어야 한다는 것입니다.

    플랫폼이 완전히 처리할 수 없는 옵션을 구매자가 선택하면, 플랫폼은 continue_url로 비즈니스의 체크아웃에 넘겨야 합니다(SHOULD).

    가능한 방법¶

    가능한 방법(available methods)은 상품을 특정 방법으로 풀필먼트할 수 있는지, 그리고 언제 가능한지를 나타냅니다. 다음과 같은 경우에 씁니다.

    • 대체 방법: "이 바지는 Downtown Store에서 픽업도 가능합니다"
    • 나중에 풀필먼트: 예약 주문, 먼 창고에서 출고되는 상품, 매장에 재고가 들어오면 픽업
    {
  "ucp": { ... },
  "id": "...",
  "status": "...",
  "currency": "...",
  "line_items": [ ... ],
  "totals": [ ... ],
  "links": [ ... ],
  "fulfillment": {
    "methods": [
      {
        "id": "shipping",
        "type": "shipping",
        "line_item_ids": ["shirt", "pants"]
      },
      {
        "id": "pickup",
        "type": "pickup",
        "line_item_ids": []
      }
    ],
    "available_methods": [
      {
        "type": "shipping",
        "line_item_ids": ["shirt", "pants"],
        "fulfillable_on": "now"
      },
      {
        "type": "pickup",
        "line_item_ids": ["pants"],
        "fulfillable_on": "2026-12-01T10:00:00Z",
        "description": "Available for pickup at Downtown Store today at 2pm"
      }
    ]
  }
}

    플랫폼은 description 필드로 구매자에게 대안을 보여 줄 수 있습니다.

    🤖 셔츠와 바지는 $5에 배송되며 5~8일 후 도착합니다. 또는 바지는 4시간 후 Downtown Store에서 픽업할 수 있습니다.

    구매자가 픽업을 선택했는데 플랫폼이 분할 풀필먼트를 지원하지 않으면, 플랫폼은 continue_url로 비즈니스의 체크아웃에 넘겨야 합니다(SHOULD).

    카탈로그 디스커버리¶

    풀필먼트 확장이 카탈로그 기능을 확장하면, 카탈로그 응답의 각 변형에 fulfillment 객체가 붙어 그 변형에서 이용할 수 있는 풀필먼트 방법과 가용성을 나열합니다. 덕분에 카탈로그를 둘러보는 구매자가 상품을 어떻게 받을 수 있는지 알 수 있습니다.

    방법¶

    fulfillment.methods[]는 변형에서 이용할 수 있는 방법을 나열합니다. 각 방법에는 다음 항목이 있습니다.

    • type — 풀필먼트 방법(예: shipping, pickup). 방법 유형 참고
    • description — 이 방법으로 변형을 어떻게 풀필먼트하는지 구매자에게 알려 주는 짧은 요약(예: "Ships in 2–4 business days"). 바로 렌더링할 수 있습니다. 렌더링 참고
    • availability — 지정되었거나 추론된 위치에서 이 방법으로 변형을 이용할 수 있는지 여부
    • location — pickup 같은 장소 기반 방법에서 그 방법에 대해 확정된 위치이자 해당 장소를 가리키는 비즈니스의 안정적인 식별자. location에서 픽업할 수 있다고 알린 비즈니스는 체크아웃에서 해당 방법의 selected_destination_id로 같은 ID를 반드시 수락해야 합니다(MUST). 비즈니스는 현재 가용성과 조건을 다시 검증합니다. 디스커버리 단계에서 재고가 확보되거나 자격이 보장되지는 않으며, 선택 계약은 ID의 출처와 무관합니다. 선택과 위치 식별 참고
    • options — 이 방법 안의 구체적인 풀필먼트 선택지(예: Standard, Express). 옵션 참고. 선택 사항

    카탈로그는 방법마다 위치 하나, 즉 fulfills_to로 지정되었거나 context에서 추론된 위치에 대한 가용성만 보고합니다. 다른 위치를 찾아 비교하는 일은 별도로 처리합니다.

    변형 수준의 availability는 변형을 어떤 방법으로든 받을 수 있는지를 나타냅니다. 특정 방법에 대해서는 그 방법의 availability가 권위를 가집니다. 방법에 availability가 명시되어 있으면 소비자는 그 방법에 대해 반드시 그 값을 사용해야 하며(MUST), 변형 수준의 값으로 방법별 가용성을 추론해서는 안 됩니다(MUST NOT).

    옵션¶

    방법에는 options[]가 있을 수 있습니다(MAY). 이는 풀필먼트 옵션의 전체 목록이 아니라 대표적인 일부입니다. 목적지나 전체 장바구니를 모르는 상태라면 비즈니스는 구매자에게 의미 있는 양 끝의 옵션(예: 가장 저렴한 옵션, 가장 빠른 옵션)을 미리 보여 줘야 합니다(SHOULD). 더 구체적인 옵션은 라인 아이템과 목적지가 정해진 뒤 체크아웃에서 협상합니다.

    각 옵션에는 id와 title(형제 옵션과 구분되는 짧은 레이블)이 있고, 맥락을 설명하는 렌더링 가능한 description이 선택적으로 붙습니다. 이것이 공통 기반입니다. 체크아웃에서는 같은 옵션에 비용과 시점 정보(totals, 운송사, 풀필먼트 시간)가 더해집니다. 옵션은 열린 구조이므로 비즈니스가 필드를 추가로 덧붙일 수 있습니다(MAY). 옵션 없이 type, description, availability만 보여 주는 방법도 있을 수 있습니다(MAY). 옵션은 그룹 계층 없이 방법 바로 아래에 중첩됩니다(체크아웃의 methods[].groups[].options[]와 다릅니다).

    디스커버리에서 얻은 옵션 id로 구매자의 선택을 체크아웃까지 이어 갈 수 있습니다. 비즈니스는 체크아웃에서 같은 ID를 methods[].groups[].selected_option_id로 수락해야 합니다(SHOULD). 이 ID는 최선의 노력(best-effort) 수준의 핸들일 뿐, 같은 옵션이 나온다고 보장하지 않습니다. 체크아웃에서는 다른 상품, 수량, 합배송에 따라 옵션이 바뀌므로, 단일 상품 기준으로 찾은 옵션이 체크아웃에서는 달라질 수 있습니다.

    형태¶

    카탈로그 풀필먼트¶

    카탈로그 변형을 풀필먼트하는 방식. 체크아웃 fulfillment와 같은 구조입니다.

    이름 타입 필수 여부 설명
    methods Array[object] 선택 이 변형의 풀필먼트 방식.

    카탈로그 풀필먼트 방법¶

    카탈로그 변형의 풀필먼트 방법: 변형을 어떻게 풀필먼트할 수 있는지와 그 재고 상황.

    이름 타입 필수 여부 설명
    type string 필수 풀필먼트 방식 유형. 잘 알려진 값: shipping, pickup. 비즈니스는 추가 값을 사용할 수 있습니다(MAY).
    description object 선택 구매자에게 보여 주는 짧은 요약(예: 'Ships in 2–4 business days').
    availability object 선택 지정되거나 추론된 장소에서 이 방법으로 이 변형을 구할 수 있는지 여부.
    location string 선택 이 장소 기반 풀필먼트 방식에 대해 결정된 비즈니스 위치의 안정적이고 불투명한 식별자. 해당 방식의 selected_destination_id로 같은 ID가 제출되면 비즈니스가 이를 인식합니다. 인식했다고 해서 재고를 예약하거나 적격성을 보장하지는 않으며, 현재 조건은 다시 검증됩니다.
    options Array[object] 선택 이 방식의 대표 풀필먼트 옵션(예: Standard, Express)입니다. 배송지나 전체 장바구니가 없을 때 비즈니스는 의미 있는 양극단 옵션(예: 가장 저렴한 옵션, 가장 빠른 옵션)을 미리 보여 줘야 합니다(SHOULD). 더 구체적인 옵션은 라인 아이템과 배송지가 정해진 뒤 체크아웃에서 협상합니다.

    풀필먼트 옵션 기반¶

    이름 타입 필수 여부 설명
    id string 필수 이 풀필먼트 옵션의 고유 식별자.
    title string 필수 형제 옵션과 이 옵션을 구분하는 짧은 레이블(예: 'Standard', 'Express Shipping', 'Curbside Pickup').
    description Description 선택 제목을 보충하는 맥락 정보(예: 'Arrives in 4 business days', 'Arrives Dec 12-15 via FedEx'). 그대로 렌더링할 수 있으며, 제목을 반복해서는 안 됩니다(MUST NOT).

    가용성¶

    이름 타입 필수 여부 설명
    available boolean 선택 구할 수 있는지 여부. 풀필먼트 세부 정보는 status를 참고하세요.
    status string 선택 available을 풀필먼트 상태로 세분화합니다. 잘 알려진 값: in_stock, backorder, preorder, out_of_stock, discontinued.

    풀필먼트 목적지 필터¶

    이름 타입 필수 여부 설명
    address_country string 선택 2자리 ISO 3166-1 alpha-2 코드로 표기한 국가(예: "US"). 3자리 alpha-3 코드나 전체 국가명을 사용할 수도 있습니다(MAY).
    address_region string 선택 국가 안의 1차 행정 구역(예: California 같은 주 또는 도).
    postal_code string 선택 우편번호(예: "94043").
    location string 선택 목적지 참조(예: 매장, 픽업 장소, 저장된 주소).

    위치와 방법: context와 filters¶

    • context에는 비즈니스가 availability를 보고할 때 참고하는 구속력 없는 힌트가 담깁니다. 구매자가 있는 곳을 나타내는 대략적인 지역 필드와, 잠정적 비즈니스 위치를 나타내는 location입니다(위치 컨텍스트 참고). 시장 범위가 정해진 카탈로그에서는 비즈니스가 이 힌트로 결과를 좁힐 수 있습니다(MAY). 그 밖의 경우에는 힌트가 결과를 제거하지 않고 주석만 덧붙입니다.
    • filters.fulfills_to는 상품을 풀필먼트받을 곳입니다. 단일 목적지 (풀필먼트 목적지 필터)이며, 값(대략적인 지역)이나 참조(location id, 즉 매장, 픽업 지점, 저장된 주소)로 지정합니다. 플랫폼은 둘 중 하나만 제공해야 하며(SHOULD), 둘 다 있으면 비즈니스는 더 구체적인 쪽(보통 location)을 사용해야 합니다(SHOULD). 이 필터는 결과를 그곳으로 풀필먼트할 수 있는 상품으로 제한하고 방법별 availability의 기준이 되며, context와 다를 수 있습니다(예: 선물).
    • filters.methods는 결과를 특정 방법 유형(예: ["pickup"])으로 제한합니다.

    context는 힌트일 뿐이고, 목적지를 지정하는 것은 fulfills_to입니다. 우선순위 규칙은 위치 컨텍스트를 참고하세요.

    예시¶

    한 변형이 두 가지 풀필먼트 방법을 제공하는 예입니다. 하나는 구매자의 배송지로 배송하는 방법이고, 다른 하나는 지정된 매장에서 오늘 픽업하는 방법입니다. 방법마다 가용성이 따로 있으며, pickup은 확정된 위치를 id로 참조합니다.

    {
  "ucp": { "version": "2026-08-25" },
  "products": [
    {
      "id": "prod_kettle",
      "title": "Electric Kettle",
      "description": { "plain": "1.7L electric kettle." },

      },

        {
          "id": "var_ss",
          "title": "Stainless Steel",
          "description": { "plain": "Stainless steel finish." },
          "price": { "amount": 4999, "currency": "USD" },
          "availability": { "available": true, "status": "in_stock" },
          "fulfillment": {
            "methods": [
              {
                "type": "shipping",
                "description": { "plain": "Ships to your address in 1–4 business days" },
                "availability": { "available": true, "status": "in_stock" },
                "options": [
                  {
                    "id": "std",
                    "title": "Standard",
                    "description": { "plain": "Arrives in 4 business days" }

    구성¶

    비즈니스와 플랫폼은 각자의 프로필에 풀필먼트 제약을 선언합니다. 비즈니스는 플랫폼 프로필을 가져와 그에 맞게 응답을 조정합니다.

    extends 배열에는 이 확장이 풀필먼트를 추가할 기능을 나열합니다. 체크아웃은 권위 있는 거래 화면이고, 카탈로그는 디스커버리용입니다. 카탈로그에서도 풀필먼트를 노출하려는 비즈니스는 extends에 카탈로그 기능을 나열하고, 체크아웃으로만 한정하려면 카탈로그 기능을 빼면 됩니다.

    플랫폼 프로필¶

    플랫폼은 platform_schema로 자신의 렌더링 능력을 선언합니다.

    이름 타입 필수 여부 설명
    supports_multi_group boolean 선택 방식당 여러 그룹을 사용할 수 있게 합니다.

    config를 생략하거나 supports_multi_group: false로 설정한 플랫폼은 단일 그룹 응답을 받습니다. 응답 형태는 항상 methods[].groups[]이며, 차이는 방법마다 groups.length가 1을 넘을 수 있느냐뿐입니다.

    기본 선언(방법당 단일 그룹, 체크아웃과 카탈로그 디스커버리 모두에서 풀필먼트 노출):

    {
  "dev.ucp.shopping.fulfillment": [
    {
      "version": "2026-08-25",
      "spec": "https://ucp.dev/2026-08-25/specification/shopping/extensions/fulfillment",
      "schema": "https://ucp.dev/2026-08-25/schemas/shopping/fulfillment.json",
      "extends": [
        "dev.ucp.shopping.checkout",
        "dev.ucp.shopping.catalog.search",
        "dev.ucp.shopping.catalog.lookup"
      ]
    }
  ]
}

    카탈로그 디스커버리를 노출하지 않는 당사자는 extends를 "dev.ucp.shopping.checkout"(문자열 형태)이나 요소가 하나인 배열로 좁힐 수 있습니다(MAY).

    옵트인 선언(비즈니스가 방법당 여러 그룹을 반환할 수 있음(MAY)):

    {
  "dev.ucp.shopping.fulfillment": [
    {
      "version": "2026-08-25",
      "spec": "https://ucp.dev/2026-08-25/specification/shopping/extensions/fulfillment",
      "schema": "https://ucp.dev/2026-08-25/schemas/shopping/fulfillment.json",
      "extends": [
        "dev.ucp.shopping.checkout",
        "dev.ucp.shopping.catalog.search",
        "dev.ucp.shopping.catalog.lookup"
      ],
      "config": { "supports_multi_group": true }
    }
  ]
}

    비즈니스 프로필¶

    비즈니스는 business_config로 지원하는 풀필먼트 구성을 선언합니다.

    이름 타입 필수 여부 설명
    multi_destination Array[object] 선택 하나의 장바구니 안에서 여러 목적지를 허용하는 방법 유형(예: 여러 주소로 나누어 배송). 목록에 있는 방법은 허용되고, 빠진 방법은 허용되지 않습니다. 열린 목록이므로 비즈니스는 어떤 방법 유형이든 나열할 수 있습니다(MAY).
    method_combinations Array[array] 선택 비즈니스가 하나의 장바구니 안에서 허용하는 방법 유형 조합. 각 내부 배열은 허용되는 방법 type 값의 집합입니다(예: 배송 + 픽업). 
    {
  "dev.ucp.shopping.fulfillment": [
    {
      "version": "2026-08-25",
      "spec": "https://ucp.dev/2026-08-25/specification/shopping/extensions/fulfillment",
      "schema": "https://ucp.dev/2026-08-25/schemas/shopping/fulfillment.json",
      "extends": [
        "dev.ucp.shopping.checkout",
        "dev.ucp.shopping.catalog.search",
        "dev.ucp.shopping.catalog.lookup"
      ],
      "config": {
        "multi_destination": [
          { "method": "shipping" }
        ],
        "method_combinations": [["shipping", "pickup"]]
      }
    }
  ]
}

    이 예시는 배송지를 여러 주소로 지정할 수 있고, 장바구니에서 배송과 픽업을 섞을 수 있다는 뜻입니다.

    비즈니스 응답 동작¶

    supports_multi_group: false(기본값)인 경우:

    • 비즈니스는 모든 상품을 방법당 단일 그룹으로 반드시 통합해야 합니다(MUST).
    • 응답은 여전히 배열 구조인 methods[].groups[]를 사용하며 groups.length === 1입니다.
    • 장바구니 상품에 필요하다면 비즈니스는 여전히 여러 방법(예: 배송 + 픽업)을 반환할 수 있습니다(MAY).

    supports_multi_group: true인 경우:

    • 비즈니스는 재고, 포장, 창고 로직에 따라 방법당 여러 그룹을 반환할 수 있습니다(MAY).
    • 그룹 선택 UI(예: 패키지별 배송 속도 선택)는 플랫폼이 렌더링합니다.

    방법 유형¶

    fulfillment_method.type(체크아웃)과 catalog_fulfillment_method.type(카탈로그)은 열린 문자열 어휘 하나를 공유합니다. 표시 방식은 방법에 구애받지 않습니다. 플랫폼은 type과 관계없이 description과 availability를 렌더링해 모든 방법을 보여 줘야 하며(SHOULD)(렌더링 참고), type을 인식하지 못한다는 이유만으로 방법을 빼지 않는 것이 좋습니다(SHOULD NOT). type을 인식하면 유형별 UX를 추가로 제공할 수 있을 뿐입니다.

    방법은 type과 풀필먼트 범위(무엇을 어디로 풀필먼트하는지)로 식별합니다. 비즈니스는 같은 범위 안의 변형(예: Standard vs Express)을 options로 모델링해야 하며(SHOULD), 옵션 수준의 세부 사항만 다른 방법을 여러 개 내보내지 않는 것이 좋습니다(SHOULD NOT). type이 같더라도 범위가 다르면 별개의 방법으로 둘 수 있습니다. 예를 들어 체크아웃에 서로 다른 목적지로 가는 shipping 방법이 두 개 있을 수 있습니다. 카탈로그에서는 한 방법이 확정된 위치 하나에 있는 단일 변형을 다루므로, type당 방법이 최대 하나가 됩니다.

    잘 알려진 값:

    값 의미
    shipping 운송사가 구매자의 주소로 배송합니다.
    pickup 구매자가 지정된 위치에서 픽업합니다.
    curbside 구매자가 차에서 내리지 않고 위치에서 픽업합니다(드라이브업).

    방법 유형 추가. type은 열린 문자열이므로 비즈니스는 소비자 쪽을 바꾸지 않고도 언제든 새 값을 도입할 수 있습니다(MAY). 비즈니스가 그 값을 알리고 filters.methods로 필터링도 지원하면, 소비자는 다른 방법과 똑같이 보여 주면 됩니다.

    예시 — home_installation 추가. 스키마 변경이나 등록이 필요 없습니다. 카탈로그와 체크아웃에서 이 값을 type으로 바로 내보내고, filters.methods: ["home_installation"]로 필터링합니다. 체크아웃 협상에 쓰려면 비즈니스 프로필 config에 그 동작을 선언합니다. 예를 들어 method_combinations에 ["shipping", "home_installation"]을 넣으면 장바구니에서 배송 상품과 설치 상품을 섞을 수 있습니다(비즈니스 프로필 참고). 카탈로그 변형의 방법에서는 다음과 같이 표현합니다.

    {
  "type": "home_installation",
  "description": { "plain": "Delivered and installed in your home" },
  "availability": {
    "available": true
  }
}
