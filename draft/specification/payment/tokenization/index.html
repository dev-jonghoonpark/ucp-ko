    토큰화 가이드¶

    OpenAPI: Tokenization API

    개요¶

    이 가이드는 토큰화 결제 핸들러를 구축하는 구현자를 위한 문서입니다. 모든 토큰화 핸들러가 따르는 공통 API, 보안 요구 사항, 준수 기준을 정의합니다.

    참고: 이 가이드의 예시는 카드 자격 증명을 사용하지만, 토큰화 패턴은 은행 계좌, 디지털 지갑, 로열티 계정 등 모든 민감한 자격 증명 유형에 적용됩니다. 규정 준수 요구 사항(예: 카드의 경우 PCI DSS)은 자격 증명 유형마다 다릅니다.

    UCP에서 여러 형태의 토큰화를 활용하는 예시는 다음과 같습니다.

    예시 사용 사례
    프로세서 토크나이저 비즈니스 또는 PSP가 토큰화와 처리를 수행
    플랫폼 토크나이저 플랫폼이 비즈니스/PSP를 위해 자격 증명을 토큰화
    암호화된 자격 증명 핸들러 플랫폼이 토큰화 대신 자격 증명을 암호화

    핵심 개념¶

    자격 증명 흐름¶

    토큰화 핸들러는 자격 증명을 소스 형태와 체크아웃 형태 사이에서 변환합니다.

    +-------------------------------------------------------------------------+
|                     Tokenization Payment Flow                           |
+-------------------------------------------------------------------------+
|                                                                         |
|   Platform has:            Tokenizer            Business receives:      |
|   Source Credential    -->  /tokenize  -->         TokenCredential      |
|                                                                         |
|   +-----------------+                      +-------------------------+  |
|   | source_         |                      | checkout_               |  |
|   | credentials     |    What goes IN      | credentials             |  |
|   |                 |<---------------      |                         |  |
|   | * pan           |                      | What comes OUT          |  |
|   | * network_token |                ----->| * token                 |  |
|   |                 |                      |                         |  |
|   +-----------------+                      +-------------------------+  |
|                                                                         |
+-------------------------------------------------------------------------+

    토큰화 핸들러는 소스 자격 증명(예: PAN 자격 증명)을 받아 체크아웃 자격 증명(예: 토큰)을 생성합니다.

    네트워크 토큰에는 이 왕복 과정이 항상 필요하지는 않습니다. 네트워크 토큰은 일치하는 크립토그램 없이는 사용할 수 없으므로, 핸들러는 network_token_credential.json을 토큰화용 소스 자격 증명으로 받을 수도 있고(MAY), 체크아웃 자격 증명으로 바로 받을 수도 있습니다(MAY). 핸들러 명세는 둘 중 어느 쪽을 받는지 반드시 명시해야 합니다(MUST).

    토큰 라이프사이클¶

    토큰은 여러 단계를 거칩니다. 핸들러 명세에는 어떤 라이프사이클 정책을 사용하는지 문서화해야 합니다.

    +--------------+    +--------------+    +--------------+    +--------------+
|  Generation  |--->|   Storage    |--->| Detokenize   |--->| Invalidation |
|              |    |              |    |              |    |              |
|Platform calls|    | Tokenizer    |    | Business/PSP |    | Token expires|
| /tokenize    |    | holds token  |    | calls        |    | or is used   |
|              |    | -> credential|    | /detokenize  |    |              |
+--------------+    +--------------+    +--------------+    +--------------+
    정책 설명 사용 사례
    일회용(Single-use) 첫 디토큰화 후 무효화 가장 안전한 권장 기본값
    TTL 기반 정해진 시간(예: 15분) 후 만료 일시적 실패 시 재시도 허용
    세션 범위 체크아웃 세션 동안 유효 여러 번의 처리 시도가 있는 복잡한 흐름

    바인딩¶

    모든 토큰화 요청에는 토큰을 특정 기능(Capability) 리소스에 묶는 binding 객체가 필요합니다.

    필드 필수 설명
    type 예 바인딩된 리소스를 소유한 기능. 예: dev.ucp.shopping.checkout
    id 예 해당 기능 내에서 바인딩된 리소스의 불투명 식별자. 호출자는 반드시 비어 있지 않은 문자열을 보내야 합니다(MUST)

    바인딩 스키마를 참고하세요.

    리소스 범위와 참여자 범위는 별개입니다. 요청에서 identity는 binding 안이 아니라 그 옆에 둡니다. binding은 토큰이 어떤 리소스용인지, identity는 어떤 참여자용인지를 나타냅니다. identity는 호출자가 다른 참여자를 대신해 동작할 때 필요하며, 인증된 호출자가 바로 그 참여자일 때는 생략합니다. 결제 신원 스키마를 참고하세요.

    바인딩은 리소스 참조가 아니라 재전송(replay) 방지 장치입니다. 모든 토크나이저에 다음 규칙이 적용됩니다.

    1. 토크나이저는 반드시 type과 id가 정확히 일치하는지로 바인딩을 검증해야 합니다(MUST). 토크나이저는 부분 일치를 허용해서는 안 되며(MUST NOT), binding에 인식하지 못하는 멤버가 있다는 이유로 요청을 거부해서도 안 됩니다(MUST NOT). 비교할 때 인식하지 못하는 멤버는 반드시 무시해야 합니다(MUST). 추가 binding 멤버를 정의하는 확장은 그 멤버가 비교 대상인지 반드시 명시해야 하며(MUST), 그 확장을 구현하는 토크나이저는 반드시 확장의 정의를 따라야 합니다(MUST).
    2. 토크나이저는 반드시 binding.id를 불투명한 값으로 취급해야 합니다(MUST). 즉, 값을 해석할 수 있어야 한다고 요구해서는 안 되며(MUST NOT), 식별된 리소스의 존재를 확인할 수 없다는 이유로 요청을 거부해서도 안 됩니다(MUST NOT).
    3. 토크나이저는 binding.type을 인식하지 못한다는 이유만으로 요청을 거부해서는 안 됩니다(MUST NOT). 그래서 지금은 기능 하나만 지원하는 토크나이저도 구현을 바꾸지 않고 나중에 정의되는 기능에서 계속 사용할 수 있습니다.
    4. 모든 토큰은 정확히 하나의 참여자에게 발급됩니다. 토크나이저는 /tokenize 시점에 그 참여자를 반드시 기록해야 합니다(MUST). identity가 있으면 그 값을, 없으면 인증된 호출자를 기록합니다. /detokenize에서 토크나이저는 요청한 참여자를 같은 방식으로 반드시 결정해야 하고(MUST), 그 참여자가 발급 시 기록된 참여자와 일치하는지 반드시 검증해야 하며(MUST), 인증된 호출자가 그 참여자 본인이거나 그 참여자를 대신해 동작할 권한이 있는지 반드시 검증해야 합니다(MUST). 두 검사 중 하나라도 실패하면 토크나이저는 자격 증명을 반환해서는 안 됩니다(MUST NOT). identity는 자격 증명이 아니라 참여자 식별자이므로, 토크나이저는 이를 인증 수단으로 받아들여서는 안 됩니다(MUST NOT). 한 참여자가 다른 참여자를 대신해 동작할 권한을 얻는 방식은 핸들러가 정의하며, 이 명세의 범위에 포함되지 않습니다.

    OpenAPI¶

    토큰화 핸들러가 구현하는 엔드포인트는 두 개입니다. 핸들러는 아키텍처에 따라 하나 또는 둘 다 구현할 수 있습니다(MAY). 자체 암호화 메커니즘을 정의하는 암호화 페이로드 예시처럼 하나도 구현하지 않을 수도 있습니다.

    POST /tokenize¶

    원시 자격 증명을 토큰으로 변환합니다. 이 토큰은 기능 리소스에 바인딩되고 참여자에게 발급됩니다.

    구현 시점: 내부적으로 토큰을 생성하는 에이전트가 아니라면 항상 구현합니다.

    POST /tokenize
Content-Type: application/json

{
  "credential": {
    "type": "pan",
    "number": "4111111111111111",
    "expiry_month": 12,
    "expiry_year": 2026,
    "cvc": "123"
  },
  "binding": {
    "type": "dev.ucp.shopping.checkout",
    "id": "abc123"
  },
  "identity": {
    "access_token": "merchant_001"
  }
}

    응답:

    {
  "token": "tok_abc123xyz789"
}

    POST /detokenize¶

    유효한 토큰을 받으면 원래의 자격 증명을 반환합니다. 바인딩이 일치해야 합니다.

    구현 시점: 디토큰화를 처리와 결합하지 않는 한 항상 구현합니다(PSP 예시 참고).

    POST /detokenize
Content-Type: application/json
Authorization: Bearer {caller_access_token}

{
  "token": "tok_abc123xyz789",
  "binding": {
    "type": "dev.ucp.shopping.checkout",
    "id": "abc123"
  }
}

    응답:

    {
  "type": "pan",
  "number": "4111111111111111",
  "expiry_month": 12,
  "expiry_year": 2026,
  "cvc": "123"
}

    참고: 인증된 호출자가 토큰을 발급받은 참여자라면 identity를 생략합니다. 다른 참여자를 대신해 동작할 때(예: PSP가 비즈니스를 위해 디토큰화하는 경우)는 포함합니다.

    전체 요청/응답 스키마는 OpenAPI 명세 전문을 참고하세요.

    보안 요구 사항¶

    요구 사항 설명
    바인딩 필수 재사용을 막기 위해 자격 증명은 반드시 binding 리소스(type과 id)에 바인딩되고 정확히 하나의 참여자에게 발급되어야 합니다(MUST)
    바인딩 검증 토크나이저는 자격 증명을 반환하기 전에 반드시 바인딩 일치 여부를 검증해야 합니다(MUST)
    암호학적 난수 안전한 난수 생성기를 사용합니다. 토큰은 추측할 수 없어야 합니다
    충분한 길이 최소 128비트의 엔트로피
    비가역성 토큰에서 자격 증명을 도출할 수 없어야 합니다
    범위 제한 토큰은 해당 토크나이저에서만 동작해야 합니다
    시간 제한 사용 사례에 맞는 TTL을 적용합니다(일반적으로 5~30분)
    일회용 권장 가능하면 첫 디토큰화 후 무효화합니다

    핸들러 명세 요구 사항¶

    핸들러를 게시할 때 명세 문서에는 반드시 다음 내용을 포함해야 합니다(MUST).

    요구 사항 예시
    고유한 핸들러 이름 com.example.tokenization_payment (역 DNS 형식)
    엔드포인트 URL 프로덕션 및 샌드박스 기본 URL
    인증 요구 사항 OAuth 2.0, API 키 등
    온보딩 절차 참여자가 등록하고 신원을 발급받는 방법
    허용되는 자격 증명 토큰화에 허용되는 자격 증명 유형
    토큰 라이프사이클 정책 일회용, TTL, 또는 세션 범위
    보안 책임 동의 원시 자격 증명을 받는 참여자는 책임을 수락해야 합니다

    명세 개요 예시¶

    **Handler Name:** `com.acme.tokenization_payment`
**OpenAPI:** [Tokenization API](site:handlers/tokenization/openapi.json)

| Environment | Base URL                           |
| :---------- | :--------------------------------- |
| Production  | `https://api.acme.com/ucp`         |
| Sandbox     | `https://sandbox.api.acme.com/ucp` |

**Supported Instruments:**

| Instrument | Source Credentials           | Checkout Credentials |
| :--------- | :--------------------------- | :------------------- |
| `card`     | `pan`, `network_token`       | `token`              |

**Token Lifecycle:** Single-use (invalidated after detokenization)

**Authentication:** OAuth 2.0 client credentials

**Onboarding:** Register at portal.acme.com. Businesses receive `access_token` for handler identity.

    준수 체크리스트¶

    토크나이저 핸들러가 다음을 모두 충족하면 이 패턴을 준수하는 것입니다.

    • 고유한 역 DNS 형식의 handler_name과 함께 안정적인 URL에 핸들러 명세를 게시합니다
    • OpenAPI에 따라 /tokenize와 /detokenize 중 하나 또는 둘 다를 구현합니다
    • 인증 및 온보딩 요구 사항을 정의합니다
    • 소스 형태와 체크아웃 형태 사이의 자격 증명 변환을 문서화합니다
    • TokenCredential 스키마와 호환되는 토큰을 생성합니다
    • 토큰 라이프사이클 정책(TTL, 일회용 등)을 명시합니다
    • 토큰화 요청에 type과 id를 포함한 binding을 요구합니다
    • 참여자 식별에 PaymentIdentity를 사용합니다
    • 디토큰화 요청에서 binding이 정확히 일치하는지 검증합니다
    • 각 토큰을 발급받은 참여자를 기록하고, 디토큰화 시 그 참여자와 호출자의 대리 권한을 모두 검증합니다
    • 인식하지 못하는 바인딩 유형도 허용합니다
    • 원시 자격 증명을 받는 참여자에게 보안 책임 동의를 요구합니다
