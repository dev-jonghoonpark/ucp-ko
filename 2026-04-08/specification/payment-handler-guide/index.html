    결제 핸들러 명세 작성 가이드¶

    소개¶

    이 가이드는 UCP 결제 핸들러를 명세할 때 쓰는 표준 구조와 용어를 정의합니다. 구현자가 일관되고 완전하며 명확한 명세를 받아 볼 수 있도록, 모든 결제 핸들러 명세는 이 구조를 따라야 합니다(SHOULD).

    목적¶

    결제 핸들러는 플랫폼, 비즈니스, 결제 제공자 사이의 "N 대 N" 상호 운용성을 가능하게 합니다. 잘 작성된 핸들러 명세는 각 참여자에 대해 다음 질문에 답해야 합니다.

    • 누가 참여하는가? 어떤 참여자가 관여하며, 각자의 역할은 무엇인가?
    • 사전 요건은 무엇인가? 어떤 온보딩이나 설정이 필요한가?
    • 어떻게 구성되는가? 어떤 구성을 공개하거나 사용하는가?
    • 어떻게 실행되는가? 결제 수단을 획득하거나 처리하기 위해 어떤 프로토콜을 따르는가?

    이 가이드는 모든 핸들러 명세가 이 질문들에 체계적으로 답할 수 있도록 프레임워크를 제공합니다.

    적용 범위¶

    이 가이드의 적용 대상은 다음과 같습니다.

    • 핸들러(예: com.google.pay, dev.shopify.shop_pay) — 특정 결제 방법의 구현

    핵심 개념¶

    모든 결제 핸들러 명세는 아래 핵심 요소를 반드시 정의해야 합니다(MUST).

    프로토콜 시그니처에 관한 참고:: 이 섹션의 함수 시그니처(예: PROCESSING(...))는 실제 함수 호출이 아니라 논리적 데이터 흐름을 나타냅니다. 명세 작성자는 이 논리적 흐름을 자신의 구현에서 쓰는 실제 전송 프로토콜에 대응시켜야 합니다.

    +------------------------------------------------------------------------------+
|                        Payment Handler Framework                             |
+------------------------------------------------------------------------------+
|                                                                              |
|   +--------------+                                                           |
|   | PARTICIPANTS |  Who participates in this handler?                        |
|   +------+-------+                                                           |
|          |                                                                   |
|          v                                                                   |
|   +--------------+                                                           |
|   |PREREQUISITES |  How does each participant obtain identity & configs?     |
|   +------+-------+                                                           |
|          |                                                                   |
|          +--------------------+----------------------+                       |
|          v                    v                      v                       |
|   +--------------+    +--------------+      +--------------+                 |
|   |   HANDLER    |    |  INSTRUMENT  |      |  PROCESSING  |                 |
|   | DECLARATION  |    |  ACQUISITION |      |              |                 |
|   +--------------+    +--------------+      +--------------+                 |
|   Business advertises  platform acquires     Participant                     |
|   handler config       checkout instrument   processes instrument            |
|                                                                              |
+------------------------------------------------------------------------------+

    참여자¶

    정의: 결제 핸들러의 수명 주기에 참여하는 개별 행위자. 모든 핸들러에는 최소 두 참여자(비즈니스와 플랫폼)가 있으며, 특정 역할을 맡는 참여자를 추가로 정의할 수 있습니다(MAY).

    용어에 관한 참고:: 이 가이드에서는 해당 참여자를 "비즈니스(Business)"라고 부르지만, 기술적인 스키마 필드에는 업계 표준 명칭인 merchant_*(예: merchant_id, merchant_name)가 그대로 남아 있을 수 있습니다. 명세에는 이런 필드 대응 관계를 반드시 명시적으로 문서화해야 합니다(MUST).

    표준 참여자:

    참여자 역할
    비즈니스 핸들러 구성 공개, 결제 수단 처리
    플랫폼 핸들러 탐색, 결제 수단 획득, 체크아웃 제출

    확장 참여자(핸들러별 참여자 예시):

    참여자 역할 예시
    토크나이저(Tokenizer) 원본 자격 증명 저장, 토큰 자격 증명 발급
    PSP 체크아웃 결제 수단으로 비즈니스를 대신해 결제 처리

    사전 요건¶

    정의: 참여자가 핸들러 흐름에 참여하기 전에 완료해야 하는 온보딩, 설정 또는 구성.

    시그니처:

    PREREQUISITES(participant, onboarding_input) → prerequisites_output
    필드 설명
    participant 온보딩 대상 참여자(비즈니스, 플랫폼 등)
    onboarding_input 참여자가 설정 과정에서 제공하는 정보
    prerequisites_output 받은 신원 정보와 추가 구성

    사전 요건 출력:

    prerequisites_output에는 참여자가 온보딩에서 받는 내용이 담깁니다. 최소한 신원(identity)은 포함됩니다(결제 신원 참고). 핸들러별 추가 구성, 자격 증명, 설정도 포함할 수 있습니다(MAY).

    결제 핸들러 명세에서 prerequisites_output의 정식 스키마를 정의할 필요는 없습니다. 대신 명세에 다음 내용을 명확히 문서화해야 합니다(SHOULD).

    • 어떤 신원이 할당되는지(그리고 PaymentIdentity에 어떻게 대응하는지)
    • 어떤 추가 구성이 제공되는지
    • 사전 요건 출력이 핸들러 선언, 결제 수단 획득, 처리 단계에서 어떻게 쓰이는지

    참고:

    • 사전 요건은 보통 대역 외(out-of-band)에서 처리합니다(포털, 계약, API 호출).
    • 참여자마다 독립적인 사전 요건이 있을 수 있습니다(MAY).
    • 사전 요건에서 받은 신원은 보통 핸들러의 config 객체 안에 들어갑니다(예: merchant_id 또는 이와 비슷한 핸들러별 필드).
    • 원본 자격 증명을 받는 참여자(예: 비즈니스, PSP)는 보통 온보딩 중에 보안 확인 절차를 마쳐, 자격 증명 처리와 규정 준수에 대한 책임을 수락해야 합니다.

    핸들러 선언¶

    정의: 비즈니스가 이 핸들러를 지원한다는 사실을 나타내며, 플랫폼이 핸들러를 호출할 수 있도록 공개하는 구성.

    시그니처:

    HANDLER_DECLARATION(prerequisites_output) → handler_declaration
    필드 설명
    prerequisites_output 비즈니스 사전 요건에서 얻은 신원과 구성
    handler_declaration ucp.payment_handlers에 공개되는 핸들러 객체

    출력 구조:

    핸들러 선언은 PaymentHandler 스키마를 따릅니다. 명세는 사용 가능한 구성 스키마와 결제 수단 스키마를 정의하고, 비즈니스의 사전 요건 출력과 원하는 구성을 바탕으로 각각을 어떻게 구성하는지 정의해야 합니다(SHOULD).

    {
  "ucp": {
    "payment_handlers": {
      "com.example.handler": [
        {
          "id": "processor_tokenizer_1234",
          "version": "2026-04-08",
          "spec": "https://example.com/ucp/handler",
          "schema": "https://example.com/ucp/handler/schema.json",
          "available_instruments": [
            // Instrument types this handler supports
          ],
          "config": {
            // Handler-specific configuration (see Config Shapes)
          }
        }
      ]
    }
  }
}

    available_instruments 필드는 선택 사항입니다. 이 필드가 없으면 핸들러는 결제 수단 유형이나 제약 조건을 전혀 제한하지 않으며, 핸들러 스키마가 정의하는 모든 결제 수단 유형을 지원합니다. 이 필드가 있으면 공개하는 유형을 좁히거나 추가 제약 조건을 적용합니다(예: 카드 브랜드를 ["visa", "mastercard"]로 제한).

    핸들러 선언 변형¶

    PaymentHandler 스키마는 맥락에 따라 세 가지 변형을 정의합니다. 기술적으로 필수인 것은 id와 version뿐이지만, 변형마다 목적이 다르고 보통 담기는 구성도 다릅니다.

    변형 맥락 목적
    business_schema 비즈니스 디스커버리(/.well-known/ucp) 비즈니스 신원과, 비즈니스가 이 핸들러를 어떻게 구성했는지 선언합니다. 판매자별 설정을 담습니다.
    platform_schema 플랫폼 프로필(공개된 URI) 플랫폼 신원과, 플랫폼이 이 핸들러를 어떻게 지원하는지 선언합니다. 구현자를 위한 spec, schema URL을 포함합니다.
    response_schema 체크아웃/주문 API 응답 확정된 맥락을 담은 런타임 구성: 판매자 신원, 이 체크아웃에 확정된 available_instruments, 토큰화 명세, 거래 처리에 필요한 기타 상태. 플랫폼은 반드시 이 구성을 권위 있는 정보로 취급해야 합니다(MUST).

    비즈니스 스키마 예시(비즈니스가 핸들러 구성을 선언):

    {
  "id": "processor_tokenizer_1234",
  "version": "2026-04-08",
  "spec": "https://example.com/ucp/handler",
  "schema": "https://example.com/ucp/handler/schema.json",
  "available_instruments": [
    {
      "type": "card",
      "constraints": {
        "brands": ["visa", "mastercard"]
      }
    }
  ],
  "config": {
    "environment": "production",
    "business_id": "business_xyz_789"
  }
}

    플랫폼 스키마 예시(플랫폼이 핸들러 지원을 선언):

    {
  "id": "platform_tokenizer_2345", // note: ids are for disambiguation, they may differ between business and platform
  "version": "2026-04-08",
  "spec": "https://example.com/ucp/handler",
  "schema": "https://example.com/ucp/handler/schema.json",
  "available_instruments": [
    {
      "type": "card",
      "constraints": {
        "brands": ["visa", "mastercard", "amex", "discover"]
      }
    }
  ],
  "config": {
    "environment": "production",
    "platform_id": "platform_abc_123"
  }
}

    응답 스키마 예시(체크아웃의 런타임 맥락):

    {
  "id": "processor_tokenizer_1234",
  "version": "2026-04-08",
  "available_instruments": [
    {
      "type": "card",
      "constraints": {
        "brands": ["visa", "mastercard"]
      }
    }
  ],
  "config": {
    "api_version": 2,
    "environment": "production",
    "business_id": "business_xyz_789"
  }
}

    available_instruments 확정¶

    플랫폼과 비즈니스는 각자의 프로필에서 따로 available_instruments를 공개합니다. 이를 response_schema로 반환할 권위 있는 값으로 확정하는 일은 비즈니스가 맡습니다.

    확정 흐름:

    1. 플랫폼이 지원 범위를 선언합니다 — 플랫폼 프로필의 각 핸들러 선언에 available_instruments가 들어 있습니다. 비즈니스는 이 값으로 플랫폼이 무엇을 처리할 수 있는지 알 수 있습니다(예: ["visa", "mastercard", "amex", "discover"]만 지원).

    2. 비즈니스가 확정합니다 — 요청을 받으면 비즈니스는 다음 항목의 교집합을 구해 해당 체크아웃에 확정된 available_instruments를 계산합니다.

    3. 플랫폼이 공개한 available_instruments(플랫폼의 지원 범위)
    4. 자신의 business_schema 선언(판매자가 실제로 받도록 설정된 결제 수단)

    5. 장바구니/체크아웃 맥락(예: 특정 상품 유형은 사용할 수 있는 결제 방법을 제한할 수 있음)

    6. 응답이 우선합니다 — response_schema의 available_instruments는 이 체크아웃에 대해 비즈니스가 확정한 선택입니다. 플랫폼은 반드시 이 값을 권위 있는 정보로 취급해야 하며(MUST), 이와 모순되는 결제 수단 유형을 사용하거나 제약 조건을 적용하려 해서는 안 됩니다(MUST NOT).

    예시:

    출처 available_instruments
    플랫폼 프로필 [{type: "card", constraints: {brands: ["visa", "mastercard", "amex", "discover"]}}]
    비즈니스 프로필 [{type: "card", constraints: {brands: ["visa", "mastercard", "amex"]}}]
    응답(확정) [{type: "card", constraints: {brands: ["visa", "mastercard", "amex"]}}]

    이 예시에서는 비즈니스의 PSP에 Discover 지원이 설정되어 있지 않으므로, 플랫폼이 Discover를 지원하더라도 응답에서 빠집니다.

    스키마 정의¶

    schema 필드는 핸들러별 형태를 정의하는 JSON 스키마를 가리킵니다. 작성자는 보통 형태마다 별도 파일을 만들어 참조합니다.

    • 구성(Config) — 플랫폼/비즈니스 선언과 런타임 응답을 위한 구성
    • 결제 수단(Instrument) — 플랫폼에 반환되는 결제 수단 구조
    • 자격 증명(Credential) — 결제 수단 안의 자격 증명 구조

  "version": "2026-04-08",

    결제 수단 형태¶

    기본 결제 수단 스키마:

    스키마 설명
    payment_instrument.json 기본: id, handler_id, type, billing_address, credential, display
    card_payment_instrument.json 기본 스키마에 표시 정보 추가: brand, last_digits, expiry, 카드 이미지

    UCP는 card 같은 범용 결제 수단용 기본 스키마를 제공합니다. 명세 작성자는 기본 결제 수단을 확장해 핸들러별 표시 데이터를 추가하거나 자격 증명 참조를 원하는 대로 바꿀 수 있습니다(MAY). 핸들러는 결제 흐름별로 여러 결제 수단 유형을 정의할 수 있습니다(MAY).

    사용 가능한 결제 수단 스키마:

    각 결제 수단 스키마는 $defs에 자체 available_* 변형을 정의하며, 이 변형은 해당 결제 수단 유형에 유효한 제약 조건을 지정합니다. 예를 들어 card_payment_instrument.json은 brands 제약 조건이 있는 available_card_payment_instrument를 정의합니다.

    스키마 제약 조건
    available_payment_instrument.json 기본: type, constraints(개방형 객체)
    card_payment_instrument.json#/$defs/available_card_payment_instrument 기본 스키마에 카드 네트워크용 constraints.brands 추가

    핸들러는 available_instruments를 선언할 때 결제 수단이 정의한 이 스키마들을 참조합니다. 어떤 제약 조건이 의미 있는지(예: 카드의 brands)는 결제 수단 스키마 작성자가 정의하고, 플랫폼/비즈니스는 이를 사용해 지원하는 항목(예: ["visa", "mastercard"])을 알립니다.

    types/tokenizer_instrument.json 예시:

    {
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.com/ucp/handlers/tokenizer/types/tokenizer_instrument.json",
  "title": "Tokenizer Card Instrument",
  "description": "Card-based payment instrument for com.example.tokenizer.",

  "$defs": {
    "available_tokenizer_card": {
      "title": "Available Tokenizer Card",
      "description": "Card instrument availability with tokenizer-specific constraints.",
      "allOf": [
        { "$ref": "https://ucp.dev/2026-04-08/schemas/shopping/types/card_payment_instrument.json#/$defs/available_card_payment_instrument" },
        {
          "type": "object",
          "properties": {
            "type": { "const": "tokenizer_card" },
            "constraints": {
              "type": "object",
              "properties": {
                "tokenization_types": {
                  "type": "array",
                  "items": { "type": "string" },
                  "description": "Supported tokenization types (e.g., ['network_token', 'merchant_token'])."
                }
              }
            }
          }
        }
      ]
    }
  },

  "allOf": [
    { "$ref": "https://ucp.dev/2026-04-08/schemas/shopping/types/card_payment_instrument.json" }
  ],
  "type": "object",
  "required": ["type"],
  "properties": {
    "type": { "const": "tokenizer_card" },
    "credential": {
      "oneOf": [
        { "$ref": "tokenizer_token.json" },
        { "$ref": "tokenizer_alt_token.json" }
      ]
    },
    "special_tokenizer_context": {
      "type": "object",
      "description": "Handler-specific context for tokenizer instruments."
    }
  }
}

    types/tokenizer_alt_instrument.json 예시:

    자격 증명 형태¶

    기본 자격 증명 스키마:

    스키마 설명
    payment_credential.json 기본: 유형 판별자만 포함
    token_credential.json 토큰: 유형 + 토큰 문자열

    UCP는 범용 결제 자격 증명용 기본 스키마를 제공합니다. 작성자는 이 스키마를 확장해 핸들러별 자격 증명 맥락을 포함할 수 있습니다(MAY). 핸들러는 결제 수단 흐름별로 여러 자격 증명 유형을 정의할 수 있습니다(MAY).

    명세는 핸들러가 받는 자격 증명 유형을 반드시 정의해야 합니다(MUST).

    중요: 토큰 자격 증명을 사용한다면 플랫폼이 자격 증명을 언제 갱신해야 하는지 알 수 있도록 스키마에 만료 필드(expiry, ttl 또는 비슷한 필드)를 반드시 포함해야 합니다(MUST).

    결제 수단 획득¶

    정의: 비즈니스의 체크아웃에 제출할 결제 수단을 얻기 위해 플랫폼이 따르는 프로토콜.

    시그니처:

    INSTRUMENT_ACQUISITION(
  platform_prerequisites_output,
  handler_declaration,
  binding,
  buyer_input
) → checkout_instrument
    필드 설명
    platform_prerequisites_output 사전 요건이 필요했던 경우 플랫폼의 사전 요건 출력(구성)
    handler_declaration.config 비즈니스가 제공한 핸들러별 구성
    binding (2.6 참고) 자격 증명을 특정 체크아웃에 결속하기 위한 맥락
    buyer_input 구매자의 결제 선택 또는 자격 증명
    checkout_instrument 체크아웃에 제출할 결제 수단

    결제 핸들러 명세에서 결제 수단 획득의 정식 절차를 정의할 필요는 없습니다. 대신 명세에 다음 내용을 명확히 문서화해야 합니다(SHOULD).

    • 핸들러의 config를 적용해 유효한 checkout_instrument를 만드는 방법
    • 사용 가능한 config와 checkout을 바탕으로, 보안상 매우 중요한 특정 체크아웃 및 비즈니스에 자격 증명을 효과적으로 바인딩하는 방법

    처리¶

    정의: 참여자(보통 비즈니스 또는 PSP)가 받은 결제 수단을 처리해 거래를 완료하기 위해 수행하는 단계.

    시그니처:

    PROCESSING(
  identity,
  checkout_instrument,
  binding,
  transaction_context
) → processing_result
    필드 설명
    identity 처리를 수행하는 참여자의 PaymentIdentity
    checkout_instrument 플랫폼에서 받은 결제 수단
    binding 검증을 위한 바인딩 맥락
    transaction_context 체크아웃 합계, 라인 아이템 등
    processing_result 결제 세부 정보를 포함한 성공/실패 결과

    오류 처리¶

    명세는 일반적인 실패(예: '거절(Declined)', '잔액 부족(Insufficient Funds)', '네트워크 오류(Network Error)')를 표준 UCP 오류 정의에 대응시키는 매핑을 반드시 정의해야 합니다(MUST). 그래야 플랫폼이 기반 결제 처리사와 관계없이 구매자에게 현지화되고 일관된 오류 메시지를 보여 줄 수 있습니다.

    주요 정의¶

    용어 정의
    바인딩(Binding) 결제 수단을 특정 체크아웃 거래 및 비즈니스 신원과 암호학적 또는 논리적으로 연관시키는 것. 비즈니스 A용 유효한 자격 증명을 가로채 비즈니스 B에서 쓰는 재전송(replay) 공격을 막습니다.

    명세 템플릿¶

    핸들러 명세는 표준 템플릿 구조를 사용해야 합니다(SHOULD). [REQUIRED] 표시가 있는 섹션은 반드시 있어야 하며(MUST), [CONDITIONAL] 표시가 있는 섹션은 해당하는 경우에만 필요합니다.

    → 결제 핸들러 템플릿

    명세 작성자를 위한 준수 체크리스트¶

    결제 핸들러 명세를 게시하기 전에 다음 항목을 확인하세요.

    구조¶

    • 표준 템플릿 구조를 사용합니다
    • 모든 [REQUIRED] 섹션이 있습니다
    • 해당하는 경우 [CONDITIONAL] 섹션이 있습니다

    참여자¶

    • 모든 참여자가 나열되어 있습니다
    • 각 참여자의 역할이 명확히 설명되어 있습니다
    • 해당하는 경우 "Business"와 "Merchant" 용어에 관한 참고가 추가되어 있습니다

    사전 요건¶

    • 사전 요건이 필요한 참여자마다 사전 요건 절차가 문서화되어 있습니다
    • 온보딩 입력이 명시되어 있습니다
    • 사전 요건 출력(신원 + 추가 구성)이 설명되어 있습니다
    • 신원이 PaymentIdentity 구조(access_token)에 대응됩니다

    핸들러 선언¶

    • 신원 스키마(기본 또는 확장)가 문서화되어 있습니다
    • 구성 스키마가 (해당하는 경우) 문서화되어 있고 환경(environment)을 포함합니다
    • 결제 수단 스키마(기본 또는 확장)가 문서화되어 있습니다

    결제 수단 획득¶

    • 프로토콜 단계가 빠짐없이 명확하게 나열되어 있습니다
    • 논리적 흐름이 실제 프로토콜에 대응되어 있습니다
    • API 호출이나 SDK 사용법을 예시와 함께 제시합니다
    • 바인딩 요구 사항이 명시되어 있습니다
    • 체크아웃 결제 수단의 생성 방식과 형태가 잘 정의되어 있습니다

    처리¶

    • 처리 단계가 빠짐없이 명확하게 나열되어 있습니다
    • 검증 요구 사항이 명시되어 있습니다
    • 오류 처리와 매핑을 다룹니다

    보안¶

    • 보안 요구 사항이 나열되어 있습니다
    • 바인딩 검증이 필수로 지정되어 있습니다
    • 자격 증명 처리 지침을 제공합니다
    • (해당하는 경우) 토큰 만료가 정의되어 있습니다

    일반¶

    • 핸들러 이름이 역 DNS(reverse-DNS) 규칙을 따릅니다
    • 버전이 YYYY-MM-DD 형식을 따릅니다
    • 모든 스키마 URL이 네임스페이스 권한과 일치합니다
    • 참고 자료 섹션에 모든 스키마가 포함되어 있습니다

    모범 사례¶

    품질이 높고 유지 관리하기 쉬운 핸들러 명세를 만들려면 다음 지침을 따르세요.

    스키마 설계¶

    사례 설명
    새로 만들지 말고 확장하기 allOf로 기본 스키마를 조합합니다. brand, last_digits 등을 재정의하지 않습니다.
    판별자에는 const 사용 자격 증명 유형을 모호함 없이 식별할 수 있도록 credential.type을 const로 정의합니다.
    일찍 검증하기 구현자가 검증할 수 있도록 명세를 확정하기 전에 안정적인 URL에 스키마를 게시합니다.
    만료 포함하기 토큰 자격 증명을 설계할 때는 항상 expiry 또는 ttl을 포함합니다.

    문서화¶

    사례 설명
    말로만 설명하지 말고 보여 주기 모든 스키마와 프로토콜 단계마다 완전한 JSON 예시를 포함합니다.
    오류 사례 문서화 어떤 오류가 발생할 수 있고 참여자가 어떻게 처리해야 하는지 명시합니다.
    독립적인 버전 관리 핸들러 버전은 UCP 코어 버전과 별개로 발전합니다.

    보안¶

    사례 설명
    바인딩 필수화 항상 binding으로 자격 증명을 특정 체크아웃에 결속합니다.
    자격 증명 노출 최소화 원본 자격 증명(PAN 등)이 되도록 적은 시스템만 거치도록 흐름을 설계합니다.
    토큰 수명 명시 토큰이 일회용인지, 시간 제한이 있는지, 세션 범위인지 문서화합니다.

    유지 관리성¶

    사례 설명
    안정적인 URL에 스키마 호스팅 스키마 URL은 바뀌지 않아야 합니다. 필요하면 버전이 포함된 경로를 사용합니다.
    우아하게 실패하기 일반적인 실패 시나리오마다 명확한 오류 응답을 정의합니다.
    예시 참고하기 일반적인 흐름은 기존 핸들러 명세와 토큰화 가이드를 참고하세요.
