    체크아웃 기능¶

    • 기능 이름: dev.ucp.shopping.checkout

    개요¶

    플랫폼이 체크아웃 세션을 진행할 수 있게 합니다. AP2 위임(Mandate) 확장을 지원하지 않는 한, 체크아웃은 사용자가 신뢰할 수 있는 UI에서 직접 최종 확정해야 합니다.

    비즈니스는 계속 Merchant of Record(MoR)로 남으며, 이 기능으로 카드 결제를 받더라도 PCI DSS 인증을 받을 필요가 없습니다.

    흐름 개요¶

    결제¶

    결제 핸들러는 /.well-known/ucp에 있는 비즈니스의 UCP 프로필과 checkout.ucp.payment_handlers에서 찾을 수 있습니다. 핸들러는 결제 수단(예: Google Pay, Shop Pay)을 수집하는 처리 사양을 정의합니다. 구매자가 결제를 제출하면 플랫폼은 수집한 결제 수단 데이터로 payment.instruments 배열을 채웁니다.

    payment 객체는 체크아웃 생성 시 선택 사항입니다. 결제 처리가 필요 없는 사용 사례 (예: 견적 생성, 장바구니 관리)에서는 생략할 수 있습니다.

    비즈니스는 응답의 payment.instruments를 자체 사용자 상태에 있는 표시 안전 (display-safe) 결제 수단으로 채울 수도 있습니다. 인증된 구매자가 해당 비즈니스에 저장해 둔 결제 수단이 그 예입니다. 이런 결제 수단에는 원본 자격 증명이 담기지 않습니다. 구매자가 선택하면 비즈니스가 서버 측에서 해석하는, 표시 안전하고 비즈니스 범위로 한정된 참조(불투명한 id와 display 필드)일 뿐입니다. 체크아웃 생성 REST 예시도 Shop Pay 결제 수단을 이미 이 형태로 반환합니다. 사용자별로 저장된 상태를 반환하려면 사용자 인증 요청이 필요합니다. 적용되는 제한 사항은 신원 연결을 참고하세요.

    플랫폼은 display 필드로 저장된 결제 수단을 표시하고, 구매자는 이를 보고 자신의 결제 수단을 알아볼 수 있습니다. 현재 기본 스키마는 결제 수단을 그대로 청구할 수 있는지, 아직 자격 증명 수집이 필요한지를 구분하지 않습니다. 따라서 플랫폼은 credential이 없다는 점이나 id 명명 방식만 보고 결제 준비 여부를 추론하지 않아야 합니다.

    풀필먼트¶

    UCP는 다양한 사용 사례를 수용하기 위해 풀필먼트를 확장으로 모델링합니다.

    체크아웃 객체에서 풀필먼트는 선택 사항입니다. 덕분에 플랫폼은 실물 상품에나 필요한 풀필먼트 세부 정보를 제공하지 않고도 디지털 상품을 체크아웃할 수 있습니다.

    수량과 판매 기준¶

    체크아웃은 기본 식별자(C62, 0)를 포함한 공통 수량과 단위 계약을 따릅니다. 비즈니스는 거래에서 각 상품의 권위 있는 판매 기준을 결정합니다. 비즈니스의 응답이 권위를 가지며, 각 line_items[].quantity는 해당 기준에서의 정수 스텝 수입니다.

    판매 기준 디스커버리. 판매 기준은 상품 데이터입니다. 플랫폼은 거래 전에 카탈로그에서 상품의 quantity_unit(scale과 increment 포함)을 조회해야 합니다(SHOULD). 카탈로그 정보가 없는 플랫폼은 서술자를 생략할 수 있습니다. 이때 비즈니스는 자신의 권위 있는 기준을 적용하고 응답 라인에서 그 기준을 알려 줍니다. 플랫폼은 되돌아온 서술자를 검토하고, 그 해석이 의도와 다르면 새로 알게 된 기준으로 수량을 다시 제출합니다. 플랫폼은 요청에 quantity_unit을 명시하는 방법(아래 참고)으로 이전에 확인한 기준이 여전히 유효한지 검사합니다. 기준을 모르는 플랫폼은 추측한 값을 명시하지 말고 서술자를 생략합니다.

    수량 요청. 플랫폼 요청에서 line_items[].item.quantity_unit을 생략하면 플랫폼은 판매 기준 식별자에 대해 아무것도 명시하지 않은 것이 됩니다. 비즈니스는 상품의 권위 있는 판매 기준으로 quantity를 해석합니다. 따라서 계량 단위로 판매되는 상품을 요청할 때도 기본 식별자를 명시하지 않은 채 서술자를 생략할 수 있습니다.

    플랫폼은 요청 라인에 quantity_unit을 넣어 자신이 주문한다고 생각하는 기준을 명시할 수 있습니다(MAY). 플랫폼이 이를 넣었다면 비즈니스는 반드시 명시된 기계 식별자와 권위 있는 기계 식별자를 비교해야 합니다(MUST). unit: "C62"와 실효 scale 0을 명시적으로 지정하면 서술자가 없을 때의 기본 식별자와 일치하는 것으로 봅니다. display_text가 달라도 불일치가 아닙니다.

    명시된 quantity_unit이 상품의 권위 있는 판매 기준과 일치하지 않으면, 요청한 수량은 비즈니스가 판매하지 않는 기준으로 표시된 셈입니다. 조용한 변환은 어느 방향으로든 금지됩니다. 어느 쪽도 상대가 지정한 수량을 변경 사실을 알리지 않고 재해석해서는 안 됩니다. 비즈니스는 다음 두 가지 방법 중 하나로 불일치를 해결합니다.

    • 눈에 보이게 변환합니다. 비즈니스가 명시된 기준을 자신의 권위 있는 기준으로 변환할 수 있으면(예: 파운드를 킬로그램으로), 요청을 눈에 보이는 라인 수정으로 적용할 수 있습니다(MAY). 라인에는 권위 있는 서술자와 변환된 수량이 담깁니다. 변환된 수량은 비즈니스의 규칙에 따라 권위 있는 scale로 한 번 반올림하고, 주문 증분 정책이 있으면 변환 후에 적용합니다. 응답에는 해당 라인에 대한 경고 messages[] 항목이 포함됩니다. UCP는 변환 계수나 차원을 정의하지 않으며, 변환 여부는 비즈니스가 스스로 판단합니다.
    • 복구 가능하게 거부합니다. 변환할 수 없거나 변환하지 않기로 했다면(예: 리터로 표시된 체결 부품 수량), 비즈니스는 반드시 권위 있는 기준을 명시한 복구 가능한 비즈니스 결과로 해당 라인에 대한 요청의 효과를 거부해야 합니다(MUST). 수정 요청이면 라인은 이전의 권위 있는 상태로 유지됩니다. 생성 요청이면 라인이 생성되지 않으며, 메시지의 content에 해당 상품을 밝힙니다. 생성할 수 있는 라인이 하나도 없으면 비즈니스는 대신 에러 응답을 반환할 수 있습니다(MAY).

    두 경우 모두 응답은 거부된 입력을 되돌려 주지 않고 권위 있는 상태를 반영합니다. 응답 반향 규칙에 따라, 응답에 있는 모든 라인은 권위 있는 판매 기준을 담습니다. 플랫폼은 되돌아온 서술자를 읽거나 카탈로그를 다시 읽은 뒤 재제출해서 복구합니다. 메시지 content는 사람이 읽을 설명 텍스트이므로 복구 입력으로 사용해서는 안 됩니다.

    예를 들어 한 산업용 공급업체가 낱개 체결 부품을 킬로그램 단위로 판매하는데, 플랫폼은 오래된 데이터 때문에 파운드 단위로 판매한다고 알고 있다고 합시다. 플랫폼은 그 기준을 명시해 수정 요청을 제출합니다.

    {
  "line_items": [
    {
      "id": "li_fasteners",
      "item": {
        "id": "var_fasteners",
        "quantity_unit": { "unit": "LBR", "scale": 2, "display_text": "lb" }
      },
      "quantity": 275
    }
  ]
}

    변환하는 비즈니스는 수정 요청을 눈에 보이는 수정으로 적용합니다. 라인은 권위 있는 기준으로 표시되고(요청한 2.75 lb는 1.25 kg으로 변환되어 scale 2로 한 번 반올림됨), 경고로 수정 사실을 알립니다.

    체크아웃 상태 수명 주기¶

    체크아웃의 status 필드는 세션의 현재 단계를 나타내며, 다음에 어떤 처리가 필요한지 결정합니다. 상태는 비즈니스가 설정하고, 플랫폼은 진행에 필요한 사항을 알려 주는 메시지를 받습니다.

           +------------+                         +---------------------+
       | incomplete |<----------------------->| requires_escalation |
       +-----+------+                         |   (buyer handoff    |
             |                                |  via continue_url)  |
             | all info collected             +----------+----------+
             v                                           |
    +------------------+                                 |
    |ready_for_complete|                                 |
    |                  |                                 |
    | (platform can    |                                 | continue_url
    | call Complete    |                                 |
    |   Checkout)      |                                 |
    +--------+---------+                                 |
             |                                           |
             | Complete Checkout                         |
             v                                           |
   +--------------------+                                |
   |complete_in_progress|                                |
   +---------+----------+                                |
             |                                           |
             +-----------------------+-------------------+
                                     v
                               +-------------+
                               |  completed  |
                               +-------------+

                               +-------------+
                               |  canceled   |
                               +-------------+
          (session invalid/expired - can occur from any state)

    상태 값¶

    • incomplete: 체크아웃 세션에 필수 정보가 빠졌거나 해결해야 할 문제가 있습니다. 플랫폼은 messages 배열에서 맥락을 확인하고 Update Checkout으로 해결을 시도해야 합니다. 활성 확장이 액션(Action)을 노출하면, 그 인스턴스로 비즈니스가 ready_for_complete를 반환하기 전에 완료해야 할 작업을 알 수 있습니다.

    • requires_escalation: 체크아웃 세션에 API로 제공할 수 없는 정보나 구매자의 입력이 필요합니다. 플랫폼은 무엇이 필요한지 파악하려면 messages를 확인해야 합니다(아래 에러 처리 참고). recoverable 에러가 있으면 먼저 해결합니다. 그런 다음 continue_url로 구매자에게 넘깁니다.

    • ready_for_complete: 체크아웃 세션에 필요한 정보가 모두 있어 플랫폼이 프로그래밍 방식으로 최종 확정할 수 있습니다. 미처리 액션이 남아 있지 않습니다. 플랫폼은 Complete Checkout을 호출할 수 있습니다.

    • complete_in_progress: Complete Checkout 요청이 수락되었고 비즈니스가 주문을 처리하고 있습니다. 응답에 order를 포함해서는 안 됩니다(MUST NOT). 이 상태에서는 미처리 액션이 있을 수 있습니다. 플랫폼의 진행 방법은 액션을 참고하세요.

    • completed: 주문이 접수되었습니다. order가 있으며 미처리 액션이 남아 있지 않습니다.

    • canceled: 체크아웃 세션이 유효하지 않거나 만료되었습니다. 필요하면 플랫폼은 새 체크아웃 세션을 시작해야 합니다. 미처리 액션이 남아 있지 않습니다.

    액션¶

    활성 확장에 체크아웃에 대한 미처리 작업이 있으면, 비즈니스는 해당 확장이 응답 전용 actions 맵에 선언한 액션 유형 아래에 인스턴스를 노출합니다. 공통 규칙은 개요 — 액션에 정의되어 있으며, 이 절에서는 체크아웃 상태 수명 주기에서 액션을 어떻게 해석하는지만 설명합니다. 미처리 액션에 관한 상태 불변 조건은 상태 값을 기준으로 합니다.

    모든 액션은 해당 액션 유형에 명시된 효과를 제어합니다. incomplete 상태에서는 액션으로 비즈니스가 ready_for_complete를 반환하기 전에 완료해야 할 작업을 알 수 있습니다. 액션 유형의 계약에 따라 액션을 처리한 뒤, 플랫폼은 최신 체크아웃을 얻으려면 Get Checkout을 사용하거나, complete_in_progress가 아니라면 후속 Update Checkout 응답을 사용해야 합니다(SHOULD).

    액션이 체크아웃 상태를 정하지는 않습니다. 또한 메시지의 유형이나 심각도에 따라 액션이 자신이 정의한 효과를 제어하는지가 달라지지도 않습니다. 메시지는 특정 작업의 결과를 보고할 수 있습니다. 정보나 경고 메시지는 실패를 보고하지 않고 미처리 액션을 가리킬 수 있습니다. 복구 가능한 에러 메시지는 액션을 가리켜, 그 액션 때문에 요청한 효과가 적용되지 않았다고 보고할 수 있습니다. 이때 비즈니스는 현재 체크아웃을 반환하고, 개요 — 액션에 정의된 대로 메시지의 path를 정확한 액션 항목으로 설정합니다. 메시지가 있다고 해서 액션이 관련 없는 체크아웃 작업을 막는 잠금이 되지는 않습니다.

    액션 때문에 Complete Checkout을 수락할 수 없으면 비즈니스는 반드시 status: incomplete인 현재 체크아웃과 함께, path로 해당 액션 항목을 정확히 가리키는 severity: "recoverable" 에러 메시지를 반환해야 합니다(MUST). 액션을 처리한다고 해서 거부된 Complete Checkout 요청이 재시도되지는 않습니다. 이후의 Complete Checkout 요청은 기존 멱등성 규칙을 따르는 새 작업입니다.

    수락된 완료¶

    complete_in_progress는 Complete Checkout이 수락되었다는 뜻입니다. 비즈니스가 보고하는 체크아웃 상태가 권위를 가집니다. 체크아웃이 이 상태인 동안에는 다음 작업 계약이 적용됩니다.

    작업 계약
    Get Checkout 플랫폼은 Get Checkout을 호출할 수 있으며(MAY), 비즈니스의 응답이 권위를 가집니다. 플랫폼은 액션 계약이나 플랫폼 정책이 정한 제한된 백오프로 Get Checkout을 반복할 수 있으며(MAY), 반드시 expires_at이 되면 반복 요청을 멈춰야 합니다(MUST).
    Update Checkout 플랫폼은 새 Update Checkout 작업을 시작해서는 안 됩니다(MUST NOT). 중복 요청은 계속 재전송 방지 규칙을 따릅니다. 비즈니스가 새 Update Checkout 요청을 받으면 반드시 체크아웃을 변경하지 않고 복구 가능한 에러 메시지와 함께 현재 체크아웃을 반환해야 합니다(MUST).
    Complete Checkout 플랫폼은 complete_in_progress 동안 새 Complete Checkout 작업을 시작해서는 안 됩니다(MUST NOT). 응답이 유실되었을 때의 제한적인 복구 재시도는 Complete Checkout을 참고하세요.
    Cancel Checkout 플랫폼은 Cancel Checkout을 시도하기 전에 반드시 아래의 대체 경로, 넘김, 취소 경합 규칙을 따라야 합니다(MUST).

    complete_in_progress 체크아웃에 액션이 있으면 플랫폼은 해당 액션 유형의 계약에 따라 처리합니다. 액션이 없으면 플랫폼은 Get Checkout으로 비즈니스의 처리 상황을 지켜봐야 합니다(SHOULD).

    Complete Checkout이 수락된 뒤에는 Update Checkout을 쓸 수 없으므로, 비즈니스는 Update Checkout으로 입력받아야 하는 액션을 반드시 Complete Checkout을 수락하기 전에 모두 노출해야 합니다(MUST).

    확장이 정의한 액션 처리가 끝난 뒤에도 비즈니스가 그 결과를 받아 반영하기까지 시간이 걸릴 수 있습니다. 액션 완료 신호가 체크아웃 상태를 결정하지는 않습니다. 플랫폼은 반드시 Get Checkout으로 비즈니스가 결과를 반영했는지(예: 액션을 제거하거나 체크아웃 상태를 변경했는지) 확인해야 합니다(MUST).

    같은 액션 키와 id가 남아 있으면, 해당 계약이 재시도를 명시적으로 허용하고 안전한 재시도 조건을 모두 충족하지 않는 한 플랫폼은 그 액션을 다시 처리해서는 안 됩니다(MUST NOT). 새 id로 대체된 액션은 새 작업입니다. 액션이 사라지면 그 액션은 더 이상 미처리 상태가 아닙니다.

    플랫폼이 액션을 완료할 수 없거나, 비즈니스가 expires_at 이전에 액션 계약이나 플랫폼 정책이 정한 제한 시간 안에 체크아웃을 업데이트하지 않으면, 플랫폼은 적용 가능한 액션 대체 경로를 따라야 합니다(SHOULD). 어떤 대체 경로로도 체크아웃을 계속할 수 없고 continue_url을 사용할 수 있으면, 플랫폼은 이를 사용해 체크아웃을 구매자에게 넘겨야 합니다(SHOULD). 대체 경로나 넘김으로 체크아웃을 계속할 수 있는 동안에는 플랫폼이 Cancel Checkout을 시도해서는 안 됩니다(MUST NOT).

    대체 경로로도 넘김으로도 계속할 수 없으면, 플랫폼은 Get Checkout으로 최신 상태를 조회하고 여전히 complete_in_progress로 보고될 때만 Cancel Checkout을 시도해야 합니다(SHOULD). 취소는 완료와 경합할 수 있습니다. 비즈니스가 status: canceled를 보고하지 않는 한 플랫폼은 체크아웃이 취소되었다고 간주해서는 안 됩니다(MUST NOT).

    에러 처리¶

    messages 배열에는 체크아웃 상태에 관한 에러, 경고, 정보 메시지가 담깁니다. ucp.status는 형태 판별자입니다. "success"는 응답에 기대한 페이로드가 담겨 있다는 뜻이고, "error"는 그 대신 에러 정보가 담겨 있다는 뜻입니다. 각 에러 메시지에는 type, code, severity, content와, 메시지가 가리키는 특정 응답 구성 요소(필드, 라인 아이템, 액션 항목 등)를 식별하는 선택적 path가 담깁니다(아래 path 필드 참고). severity 필드는 플랫폼이 취해야 할 권장 조치를 지정합니다.

    심각도 의미 플랫폼 조치
    recoverable 플랫폼이 대역 내에서 상황을 해결할 수 있음 입력을 수정하거나 관련 액션을 처리하고, 필요하면 새 작업을 제출
    requires_buyer_input 비즈니스가 API로 받을 수 없는 입력을 요구함 continue_url로 넘김
    requires_buyer_review 구매자의 검토와 승인이 필요함 continue_url로 넘김
    unrecoverable 작업 대상 리소스가 존재하지 않음 새 리소스나 입력으로 재시도하거나 continue_url로 넘김

    requires_* 심각도의 에러가 있으면 status: requires_escalation이 됩니다. 둘 다 구매자 넘김으로 이어지지만, 서로 다른 체크아웃 상태를 나타냅니다.

    • requires_buyer_input은 체크아웃이 미완료 상태라는 뜻입니다. 비즈니스가 API로 프로그래밍 방식 수집을 지원하지 않는 정보를 요구하는 경우입니다.
    • requires_buyer_review는 체크아웃은 완료 상태이지만, 정책, 규제, 권한 규칙상 주문 접수 전에 구매자의 승인이 필요하다는 뜻입니다(예: 고액 주문 승인, 첫 구매 정책).

    비즈니스가 새 리소스를 생성할 수 없거나 요청한 리소스가 더 이상 존재하지 않으면, 응답에는 실패를 설명하는 messages와 함께 ucp.status: "error"가 담기고 응답 본문에는 리소스가 포함되지 않습니다. 작업 대상 리소스가 없으면 메시지는 severity: "unrecoverable"을 사용해야 합니다(SHOULD). 예를 들어 비즈니스는 모든 상품을 구매할 수 없는 체크아웃 생성 요청을 거부할 수 있습니다.

    {
  "ucp": { "version": "draft", "status": "error" },
  "messages": [
    {
      "type": "error",
      "code": "out_of_stock",
      "content": "All requested items are currently out of stock",
      "severity": "unrecoverable"
    }
  ],
  "continue_url": "https://merchant.com/"
}

    에러 처리 알고리즘¶

    상태가 incomplete 또는 requires_escalation이면 플랫폼은 에러를 우선순위 스택으로 처리해야 합니다. 아래 예시는 세 가지 에러 유형, 즉 복구 가능한 에러(잘못된 전화번호), 구매자 입력 요구(배송 일정 지정), 검토 요구(고액 주문)가 있는 체크아웃입니다. 뒤의 두 가지는 넘김이 필요하며 플랫폼에 보내는 명시적 신호 역할을 합니다. 비즈니스는 이런 메시지를 가능한 한 일찍 노출해야 하며(SHOULD), 플랫폼은 넘김을 시작하기 전에 복구 가능한 에러부터 해결해야 합니다(SHOULD). 복구 가능한 에러의 path가 액션 항목을 가리키면 플랫폼은 액션에 따라 처리하고, 다른 작업을 제출하기 전에 최신 체크아웃을 다시 평가합니다. 아래 예시 알고리즘은 경로가 액션을 가리키지 않는 복구 가능한 입력 에러를 다룹니다.

    [
  {
    "type": "error",
    "code": "invalid_phone",
    "severity": "recoverable",
    "path": "$.buyer.phone_number",
    "content": "Phone number format is invalid"
  },
  {
    "type": "error",
    "code": "schedule_delivery",
    "severity": "requires_buyer_input",
    "content": "Select delivery window for your purchase"
  },
  {
    "type": "error",
    "code": "high_value_order",
    "severity": "requires_buyer_review",
    "content": "Orders over $500 require additional verification"
  }
]

    에러 처리 알고리즘 예시입니다.

    GIVEN response with messages array

FILTER errors FROM messages WHERE type = "error"

PARTITION errors INTO
  recoverable           WHERE severity = "recoverable"
  requires_buyer_input  WHERE severity = "requires_buyer_input"
  requires_buyer_review WHERE severity = "requires_buyer_review"
  unrecoverable         WHERE severity = "unrecoverable"

IF unrecoverable is not empty
  RETRY with new resource or inputs, or hand off via continue_url
  RETURN

IF recoverable is not empty
  FOR EACH error IN recoverable
    IF error.path is present
      IDENTIFY the field at error.path in the request payload
      ATTEMPT to fix that field (e.g., reformat phone at $.buyer.phone_number)
    ELSE
      ATTEMPT generic fix based on error.code
  CALL Update Checkout
  RETURN and re-evaluate response

IF requires_buyer_input is not empty
  handoff_context = "incomplete, additional input from buyer is required"
ELSE IF requires_buyer_review is not empty
  handoff_context = "ready for final review by the buyer"

    표준 에러¶

    표준 에러는 플랫폼이 일반적인 에러 처리 대신 구체적이고 적절한 UX로 처리해야 하는 표준화된 에러 코드입니다.

    코드 설명
    out_of_stock 특정 상품 또는 변형을 구매할 수 없음
    item_unavailable 상품을 구매할 수 없음(예: 판매 목록에서 제외됨)
    address_undeliverable 제공된 주소로 배송할 수 없음
    payment_failed 결제 처리에 실패함
    eligibility_invalid 완료 시점에 자격 주장을 검증할 수 없음

    비즈니스는 표준 에러에 severity: recoverable을 표시해야 합니다(SHOULD). 그러면 플랫폼은 일반적인 에러 메시지를 보여 주거나 체크아웃 완료 시점까지 미루지 않고 적절한 UX(품절 안내, 주소 확인 프롬프트, 결제 수단 변경)를 제공해야 한다는 것을 알 수 있습니다.

    예: out_of_stock은 미리 구체적인 UX가 필요하지만, payment_required는 제출 시점에 일반적인 방식으로 처리해도 됩니다.

    path 필드¶

    메시지의 선택적 path 필드는 메시지를 응답 페이로드의 특정 구성 요소에 연결합니다. 플랫폼은 이 필드로 메시지를 입력 필드, 라인 아이템, 액션 항목과 연결합니다. 예를 들어 특정 구매자 필드를 강조하거나, 장바구니 라인에 표시를 하거나, 작업 결과와 관련된 액션을 찾을 수 있습니다.

    path는 반드시 UCP 응답 객체의 루트를 기준으로 하는 RFC 9535 JSONPath 표현식이어야 합니다(MUST). path를 생략하면 메시지는 응답 전체에 적용됩니다.

    단순 필드 참조:

    { "path": "$.buyer.email" }

    인덱스로 지정한 배열 요소:

    { "path": "$.line_items[0].quantity" }

    액션 항목:

    {
  "path": "$.actions['com.example.identity.student_verification'][0]"
}

    구체성 규칙: 특정 필드를 가리키는 경로(예: $.line_items[0].quantity)가 그 상위 요소를 가리키는 경로(예: $.line_items[0])보다 우선합니다. 같은 필드에 여러 에러가 적용되면 각 메시지는 적용 가능한 가장 구체적인 경로를 담아야 합니다(SHOULD).

    완료 시 자격 검증¶

    플랫폼은 context.eligibility로 구매자의 주장을 제공합니다. 로열티 멤버십, 결제 수단 혜택처럼 구매자가 자신이 받을 수 있다고 내세우는 혜택입니다. 이는 검증된 사실이 아니라 주장입니다. 비즈니스는 세션 중에 인식한 주장에 따라 조치할 수 있지만(MAY)(가격 조정, 상품 접근 허용, 잠정 할인 적용), 수락한 주장은 반드시 거래가 완료되기 전에 모두 해소해야 합니다(MUST).

    인식하지 못했거나 적용할 수 없는 주장 때문에 체크아웃이 막혀서는 안 됩니다(MUST NOT). 주장을 수락하지 않으면 비즈니스는 type: "warning" messages로 구매자에게 알려야 하며(SHOULD), 수락한 주장의 효과를 설명하는 데 type: "info"를 사용할 수 있습니다(MAY). 완료 시점까지 검증되지 않은 수락된 주장은 반드시 code: "eligibility_invalid"인 type: "error"로 처리해야 합니다(MUST)(아래 참고).

    자격 메시지 코드:

    유형 코드 발생 시점
    warning eligibility_not_accepted 주장을 인식하지 못했거나 적용할 수 없음
    info eligibility_accepted 수락된 주장의 효과
    error eligibility_invalid 완료 시점에 수락된 주장을 검증할 수 없음

    주장은 검증되거나 철회되면 해소됩니다.

    • 검증됨: 비즈니스가 증명을 바탕으로 주장을 확인합니다. UCP는 검증 방식을 규정하지 않습니다. 증명은 결제 자격 증명, 협상된 확장이 노출한 액션, 또는 플랫폼과 비즈니스가 협상한 다른 메커니즘에서 올 수 있습니다.
    • 철회됨: 플랫폼이 완료 전에 context.eligibility에서 주장을 제거합니다(예: 구매자가 결제 수단을 바꾸거나 멤버십 주장을 철회한 경우). 주장이 제거되면 비즈니스는 그 주장 없이 다시 계산합니다.

    비즈니스는 해소되지 않은 자격 주장이 남은 상태로 거래를 완료해서는 안 됩니다(MUST NOT). 검증되지 않은 주장은 잘못된 가격 책정이나 제한된 상품에 대한 무단 접근으로 이어질 수 있습니다.

    검증에 실패한 경우:

    비즈니스는 반드시 code: "eligibility_invalid", severity: "recoverable"인 에러를 messages에 반환해야 합니다(MUST). 액션이 요청한 효과를 막고 있다면 비즈니스는 반드시 액션에 명시된 대로 해당 에러 메시지의 path가 정확한 액션 항목을 가리키도록 설정해야 합니다(MUST). 그렇지 않다면 비즈니스는 path로 어떤 주장을 검증할 수 없었는지 알려야 합니다(SHOULD). 협상된 확장이 기여한 액션이나 할인 상태는 해당 확장의 규칙에 따라 현재 상태로 유지될 수 있습니다(MAY). 그러면 플랫폼은 해당 확장의 검증 흐름을 재시도하거나, Update Checkout으로 일반적인 체크아웃 변경(예: 자격이 없는 상품 제거)이나 주장 철회를 하거나, 시도를 포기할 수 있습니다(MAY).

    예시: 검증 액션으로 주장 해소하기¶

    이 예시는 설명용입니다. 여기서는 협상된 벤더 확장 com.example.identity.student_verification을 사용합니다. 이 확장은 actions 안에 같은 이름의 키로 액션 유형 하나를 선언하고, 인스턴스 config와 검증 전송 방식을 정의합니다. 이 확장을 context.eligibility, 잠정 할인, 액션, messages와 조합합니다.

    잠정 할인 필드(provisional, eligibility)는 할인 확장에 속하며, 해당 확장이 체크아웃에 활성화되어 있을 때만 사용할 수 있습니다.

    1. 주장 수락, 잠정 할인, 검증 액션 미처리. 플랫폼은 Create Checkout에서 context.eligibility에 org.example.student를 제출합니다. 비즈니스는 주장을 수락하고, 할인 확장이 활성화되어 있으므로 잠정 할인, 설명용 info 메시지, 검증 액션을 반환합니다. 주장이 아직 해소되지 않았으므로 체크아웃은 incomplete로 유지됩니다.

    {
  "ucp": { ... },
  "id": "chk_student_1",
  "status": "incomplete",
  "currency": "USD",
  "line_items": [ ... ],
  "discounts": {
    "applied": [
      {
        "title": "Student 10% Off",
        "amount": 500,
        "automatic": true,
        "provisional": true,
        "eligibility": "org.example.student"
      }
    ]
  },
  "totals": [ ... ],
  "links": [ ... ],
  "actions": {
    "com.example.identity.student_verification": [
      {
        "id": "verify-student-1",
        "config": {
          "verification_url": "https://business.example.com/verify/abc"
        }
      }
    ]
  },
  "messages": [
    {
      "type": "info",
      "code": "eligibility_accepted",
      "content": "Student discount applied provisionally. Verify your student status to keep it.",
      "path": "$.actions['com.example.identity.student_verification'][0]"
    }
  ]
}

    플랫폼은 확장이 정의한 검증 흐름을 실행합니다. 비즈니스는 대역 외(out of band)로 결과를 받습니다. 흐름이 끝나면 플랫폼은 Get Checkout으로 업데이트된 상태를 조회합니다.

    2. 검증됨. 비즈니스가 주장을 해소합니다. 검증 액션이 actions에서 제거되고, 할인이 확정되며(더 이상 provisional이 아님), 설명용 info 메시지가 갱신됩니다. 주장이 해소되었으므로 체크아웃은 ready_for_complete로 진행될 수 있습니다(MAY).

    3. 유효하지 않은 증명. 제출된 증명이 검증되지 않으면 주장은 해소되지 않은 상태로 남습니다. 비즈니스는 severity: recoverable인 eligibility_invalid 에러를 반환하며 (검증에 실패한 경우 참고), 체크아웃은 ready_for_complete에 도달하지 않습니다. 플랫폼은 유효한 증명으로 검증 흐름을 재시도하거나 주장을 철회할 수 있습니다(MAY).

    4. 철회. 플랫폼은 context.eligibility에서 주장을 제거하는 Update Checkout으로 주장을 철회합니다. 그러면 비즈니스는 잠정 할인 없이 다시 계산합니다.

    경고 표시 방식¶

    경고 메시지의 presentation 필드는 플랫폼이 반드시 따라야 하는(MUST) 렌더링 계약을 지정합니다. 생략하면 기본값은 "notice"입니다.

    notice (기본값) disclosure
    내용 표시 MUST MUST
    path와의 근접 배치 MAY MUST
    닫기 허용 MAY MUST NOT
    image_url 렌더링 MAY MUST
    url 렌더링 MAY SHOULD
    준수할 수 없을 때 에스컬레이션 — continue_url로 MUST

    notice (기본값)¶

    경고의 기본 렌더링 계약입니다. 플랫폼은 반드시 경고 내용을 구매자에게 표시해야 합니다(MUST). 플랫폼은 알림을 배너, 트레이, 토스트 형태로 렌더링할 수 있으며(MAY), 구매자가 알림을 닫도록 허용할 수 있습니다(MAY).

    disclosure¶

    presentation: "disclosure"인 경고에는 안전 경고, 알레르기 유발 물질 표시, 규정 준수 내용처럼 반드시 아래 렌더링 계약을 따라야 하는(MUST) 고지가 담깁니다.

    플랫폼 요구 사항:

    • 반드시 경고 content를 구매자에게 표시해야 합니다(MUST).
    • 고지와 그 대상의 연관성이 유지되도록 반드시 path가 참조하는 구성 요소 가까이에 경고를 표시해야 합니다(MUST). path를 생략하면 고지는 응답 전체에 적용됩니다.
    • 경고를 숨기거나, 접거나, 자동으로 닫아서는 안 됩니다(MUST NOT).
    • image_url이 있으면 반드시 렌더링해야 합니다(MUST)(예: 경고 기호, 에너지 등급 라벨).
    • url이 있으면 이동 가능한 참조 링크로 렌더링해야 합니다(SHOULD).

    presentation: "disclosure"인 경고는 일반 알림보다 렌더링 우선순위가 높아야 합니다(SHOULD).

    고지 렌더링 계약을 지킬 수 없는 플랫폼은 슬그머니 일반 알림으로 낮춰 표시하지 말고, 반드시 continue_url로 판매자 UI에 에스컬레이션해야 합니다(MUST).

    비즈니스 요구 사항:

    • 경고 내용을 특정 구성 요소와 함께 표시해야 하고 숨기거나 자동으로 닫아서는 안 되는 경우, 반드시 presentation: "disclosure"를 설정해야 합니다(MUST).
    • path 필드로 고지를 응답의 관련 구성 요소와 연결해야 합니다(SHOULD).
    • 고지 범주를 식별하는 code(예: prop65, allergens, energy_label)를 제공해야 합니다(SHOULD). 고지가 구조화된 policies[] 항목을 렌더링하는 경우, 둘을 연결할 수 있도록 code는 반드시 해당 정책의 type과 같아야 합니다(MUST) (정책 참고).
    • 고지에 관련 시각 요소(예: 경고 기호, 에너지 등급 라벨)가 있으면 image_url을 제공해야 합니다(SHOULD).
    • 구매자가 더 자세히 알아볼 수 있는 참조 링크가 있으면 url을 제공해야 합니다(SHOULD).

    고지와 확인¶

    presentation 필드는 체크아웃을 진행할 수 있는지가 아니라 경고를 어떻게 렌더링할지를 제어합니다. 구매자의 명시적인 확인이나 승인도 필요하다면, 비즈니스는 적절한 구매자 입력을 확실히 받을 수 있도록 고지를 체크아웃 상태 수명 주기에 설명된 에스컬레이션 메커니즘과 함께 사용할 수 있습니다(MAY).

    관할권과 적용 범위¶

    특정 세션에 어떤 고지가 적용되는지 판단하고 관련 있는 고지만 반환하는 일은 비즈니스가 책임집니다. 비즈니스는 관할권별 요구 사항을 판단할 때 구매자가 제공한 데이터 (context 및 기타 입력)와 상품 속성을 사용해야 합니다(SHOULD). 플랫폼은 고지 적용 범위에 관여하거나 이를 결정하지 않고, 비즈니스에게서 받은 내용을 렌더링합니다.

    Continue URL¶

    continue_url 필드를 사용하면 플랫폼에서 비즈니스 UI로 체크아웃을 넘길 수 있으므로, 구매자가 체크아웃 세션을 이어서 진행하고 최종 확정할 수 있습니다.

    제공 조건¶

    비즈니스는 status = requires_escalation을 반환할 때 반드시 continue_url을 제공해야 합니다(MUST). 그 밖의 비종료 상태(incomplete, ready_for_complete, complete_in_progress)에서는 모두 continue_url을 제공해야 합니다(SHOULD). 종료 상태(completed, canceled)에서는 continue_url을 생략해야 합니다(SHOULD).

    형식¶

    continue_url은 반드시 절대 HTTPS URL이어야 하며(MUST), 매끄럽게 넘길 수 있도록 체크아웃 상태를 보존해야 합니다(SHOULD). 비즈니스는 다음 중 한 가지 방법으로 상태 보존을 구현할 수 있습니다(MAY).

    서버 측 상태(권장)¶

    서버 측 체크아웃 상태를 기반으로 하는 불투명한 URL입니다.

    https://business.example.com/checkout-sessions/{checkout_id}
    • 서버가 checkout_id에 연결된 체크아웃 상태를 유지합니다.
    • 단순하고 안전하며, 대부분의 구현에 권장합니다.
    • URL 수명은 보통 expires_at에 연동됩니다.

    체크아웃 퍼머링크¶

    체크아웃 상태를 직접 인코딩하여 서버 측 저장 없이도 재구성할 수 있는 상태 비저장 URL입니다. 비즈니스는 체크아웃 넘김과 빠른 진입을 돕기 위해 이 형식을 지원해야 합니다(SHOULD). 예를 들어 플랫폼은 바로 구매 흐름을 시작할 때 체크아웃 상태를 미리 채울 수 있습니다.

    참고: 체크아웃 퍼머링크는 REST 전송 방식 바인딩을 확장하는 REST 전용 구성 요소입니다. 퍼머링크에 접근하면 체크아웃 UI로 리디렉션되거나 체크아웃 페이지가 바로 렌더링됩니다.

    체크아웃 생성(Create Checkout)¶

    사용자가 구매 의사를 밝혔을 때(예: 구매 버튼 클릭) 플랫폼이 호출해 상품 세부 정보로 체크아웃 세션을 시작합니다.

    권장 사항: 불일치를 줄이고 매끄러운 사용자 경험을 제공하려면, 비즈니스가 피드로 제공하는 상품 데이터(가격/제목 등)가 응답으로 반환되는 실제 속성과 일치해야 합니다(SHOULD).

    장바구니 기능이 협상된 경우, 장바구니에서 체크아웃으로 전환할 수 있도록 요청 페이로드에 cart_id 필드를 추가로 받아야 합니다. 필드 계약은 장바구니 → 장바구니에서 체크아웃으로 전환을 참고하세요.

    Inputs

    이름 타입 필수 여부 설명
    line_items Array[Line Item] 필수 체크아웃 중인 라인 아이템 목록.
    buyer Buyer 선택 구매자 정보.
    context Context 선택 관련성 판단과 현지화를 위한 잠정적 구매자 신호로, 권위 있는 데이터가 아닙니다. 검증된 입력(예: 배송 주소)이 없으면 비즈니스는 이 값을 사용해야 하며(SHOULD), 더 신뢰도 높은 신호(인증된 계정, 위험 탐지)나 규제 제약(수출 통제)과 맞지 않으면 무시하거나 우선순위를 낮출 수 있습니다(MAY). 자격 판단과 정책 적용은 반드시 체크아웃 시점에 구속력 있는 거래 데이터로 수행해야 합니다(MUST). 컨텍스트는 개인을 식별할 수 없어야 하며(SHOULD), 단계적으로 공개할 수 있습니다. 초기에는 대략적인 신호를, 세션이 진행되면서 더 세밀한 정보를 제공합니다. 더 세밀한 데이터(배송 주소, 청구 주소)가 컨텍스트보다 우선합니다.
    signals Signals 선택 승인과 악용 방지를 돕기 위해 플랫폼이 제공하는 환경 데이터. 값은 구매자가 주장한 내용이어서는 안 됩니다(MUST NOT). 플랫폼은 직접 관찰했거나 독립적으로 검증 가능한 제3자 증명에 근거한 신호를 제공합니다. 여러 확장이 공유 네임스페이스에 값을 추가할 때 출처를 보장하고 충돌을 막기 위해, 모든 신호 키는 반드시 역도메인 이름을 사용해야 합니다(MUST).
    attribution Attribution 선택 플랫폼이 내보내는 추천 및 전환 이벤트 맥락: 캠페인 식별자, 클릭 ID, source/medium 마커 등. 브라우저 기반 흐름에서 플랫폼이 URL 쿼리 매개변수로 전달하는 것과 같은 매개변수입니다.
    payment Payment 선택 핸들러를 포함한 결제 구성.

    Output

    This object MUST be one of the following types: Checkout, Error Response.

    체크아웃 조회(Get Checkout)¶

    체크아웃 리소스의 최신 상태를 제공합니다. 취소나 완료 후에 무엇을 반환할지는 비즈니스가 결정합니다(오래 유지되는 상태를 반환할 수도 있고, 일정 TTL이 지나 만료되어 'not found' 에러를 반환할 수도 있습니다). 플랫폼 측에서는 체크아웃 TTL을 따로 강제하지 않습니다.

    플랫폼은 체크아웃 세션을 생성할 때 비즈니스가 expires_at으로 알려 준 TTL을 지킵니다.

    Output

    This object MUST be one of the following types: Checkout, Error Response.

    체크아웃 완료(Complete Checkout)¶

    체크아웃에서 주문을 최종 접수하는 호출입니다. 사용자가 선택한 상품을 결제하고 주문하기로 확정했을 때 호출합니다. Complete Checkout은 ready_for_complete 상태의 체크아웃을 완료하고 주문을 접수합니다.

    응답은 체크아웃 객체입니다.

    • 완료가 동기적으로 끝나면 status는 completed이고 order 필드가 있습니다. 이 필드는 접수된 주문의 전체 상태를 참조하는 데 쓸 수 있는 id, permalink_url 같은 필수 식별자를 제공합니다.
    • 완료가 비동기 처리로 수락되면 status는 complete_in_progress이고 order는 없습니다. 플랫폼은 비즈니스 처리와 미처리 액션에 대해 수락된 완료를 따릅니다.
    • 그 밖의 상태는 핵심 체크아웃 상태 수명 주기의 의미를 그대로 따릅니다. 예를 들어 복구 가능한 변경에는 incomplete, 구매자 넘김에는 requires_escalation을 씁니다.

    플랫폼은 수락된 처리를 폴링하거나 재개하려고 Complete Checkout을 사용해서는 안 됩니다(MUST NOT). Complete Checkout의 응답을 받지 못하면 플랫폼은 제한된 백오프로 Get Checkout을 호출해 현재 상태를 확인해야 하며(SHOULD), 반드시 expires_at이 되면 중단해야 합니다(MUST). Get Checkout으로도 비즈니스가 원래 요청을 처리했는지 확인할 수 없을 때만, 플랫폼은 같은 멱등성 키로 원래와 동일한 Complete Checkout 요청을 다시 제출할 수 있습니다(MAY). 플랫폼은 이 재시도에 새 멱등성 키를 사용해서는 안 됩니다(MUST NOT). 체크아웃이 ready_for_complete로 돌아간 뒤에 실제로 새로 하는 Complete Checkout 작업에는 페이로드가 바뀌지 않았더라도 반드시 새 멱등성 키를 사용해야 합니다(MUST).

    주문을 저장할 때 Checkout의 필드로 주문 표현을 구성할 수 있습니다(MAY) (예: line_items, fulfillment 같은 정보로 초기 주문 표현을 만듭니다).

    주문이 접수된 뒤에는 주문과 관련 상품이 공급망을 거쳐 이동하면서 다른 세부 정보가 후속 이벤트로 갱신됩니다.

    signals Signals 선택 승인과 악용 방지를 돕기 위해 플랫폼이 제공하는 환경 데이터. 값은 구매자가 주장한 내용이어서는 안 됩니다(MUST NOT). 플랫폼은 직접 관찰했거나 독립적으로 검증 가능한 제3자 증명에 근거한 신호를 제공합니다. 여러 확장이 공유 네임스페이스에 값을 추가할 때 출처를 보장하고 충돌을 막기 위해, 모든 신호 키는 반드시 역도메인 이름을 사용해야 합니다(MUST).

    전송 방식 바인딩¶

    위의 추상 작업은 아래와 같이 특정 전송 프로토콜에 바인딩됩니다.

    • REST 바인딩: 표준 HTTP 메서드와 JSON 페이로드를 사용하는 RESTful API 매핑.
    • MCP 바인딩: 에이전트 상호작용을 위한 Model Context Protocol 매핑.
    • A2A 바인딩: 에이전트 상호작용을 위한 Agent-to-Agent Protocol 매핑.
    • 임베디드 체크아웃 바인딩: 임베디드 체크아웃을 구동하기 위한 JSON-RPC.

    컨텍스트¶

    컨텍스트 신호는 잠정적인 값이며 권위 있는 데이터가 아닙니다. 비즈니스는 검증된 입력(예: 배송 주소)이 없을 때 이 값을 사용해야 하며(SHOULD), 더 신뢰도 높은 신호(인증된 계정, 위험 탐지)나 규제 제약(수출 통제)과 맞지 않으면 무시하거나 우선순위를 낮출 수 있습니다(MAY). 자격 및 정책 적용은 반드시 체크아웃 시점의 구속력 있는 거래 데이터를 기준으로 해야 합니다(MUST).

    이름 타입 필수 여부 설명
    address_country string 선택 2자리 ISO 3166-1 alpha-2 코드로 표기한 국가(예: "US"). 3자리 alpha-3 코드나 전체 국가명을 사용할 수도 있습니다(MAY).
    address_region string 선택 국가 안의 1차 행정 구역(예: California 같은 주 또는 도).
    postal_code string 선택 우편번호(예: "94043").
    location string 선택 비즈니스 네임스페이스 안에서 위치(Location)를 가리키는 안정적이고 불투명한 식별자. 이 값은 잠정적이고 구속력 없는 힌트이며 구매자의 지역 정보와는 별개입니다. 효과는 작업 명세나 활성화된 기능/확장이 정의합니다. 소매 쇼핑의 흔한 예로, 사용자가 식료품을 구매할 때 선택해 저장한 기본 단골 매장 ID가 있습니다.
    intent string 선택 구매자의 의도를 설명하는 배경 맥락(예: 'looking for a gift under $50', 'need something durable for outdoor use'). 관련성, 추천, 개인화에 활용됩니다.
    language string 선택 콘텐츠의 선호 언어입니다. IETF BCP 47 언어 태그(예: 'en', 'fr-CA', 'zh-Hans')를 사용합니다. REST에서는 Accept-Language 헤더에 해당합니다. 이 필드가 없으면 플랫폼은 Accept-Language로 대체해야 하며(SHOULD), 값이 있으면 Accept-Language보다 우선합니다. 해당 언어를 제공할 수 없으면 비즈니스는 다른 언어로 콘텐츠를 반환할 수 있습니다(MAY).

    렌더링 계약¶

    제시되는 합계의 내용과 순서에 대한 권한은 비즈니스에 있습니다. 올바른 표시 방식은 비즈니스가 지켜야 하는 지역, 상품, 규제 요구 사항(예: 다중 관할권 세금 항목화, 필수 수수료 고지)에 따라 달라지기 때문입니다.

    플랫폼은 반드시 모든 최상위 항목을 제공된 순서대로 렌더링해야 합니다(MUST).

    for entry in totals:
    render_line(entry.display_text, entry.amount)

    플랫폼은 하위 라인을 보조 세부 정보로 렌더링할 수 있습니다(MAY).

    for entry in totals:
    render_line(entry.display_text, entry.amount)
    if entry.lines:
        for sub in entry.lines:
            render_detail_line(sub.display_text, sub.amount)

    플랫폼은 항목을 해석, 필터링, 재정렬, 집계하거나 자체 표시 로직을 적용해서는 안 됩니다(MUST NOT).

    totals[]의 불변 조건은 다음과 같습니다.

    • 모든 항목에는 type과 amount가 있습니다. 플랫폼은 display_text가 제공되면 이를 사용해야 합니다(SHOULD). well-known 유형에는 대체용 기본 표시 라벨이 있습니다(아래 표 참고). 알 수 없는 유형은 반드시 display_text를 포함해야 합니다(MUST).
    • 금액은 부호 있는 정수입니다. 음수 값은 차감(예: 할인), 양수 값은 가산을 뜻합니다. 부호가 곧 방향입니다.
    • type: "subtotal"은 반드시 정확히 하나 있어야 합니다(MUST).
    • type: "total"은 반드시 정확히 하나 있어야 합니다(MUST).

    검증¶

    플랫폼은 비즈니스의 값을 자체 계산한 합계로 바꿔서는 안 됩니다(MUST NOT). 플랫폼은 제공된 합계를 검증할 수 있습니다(MAY).

    assert sum(e.amount for e in totals if e.type != "total") == total_entry.amount

    계산한 합이 type: "total" 항목과 맞지 않더라도 플랫폼은 렌더링 결과를 바꿔서는 안 됩니다(MUST NOT). 표시에서는 비즈니스가 제시한 합계가 권위를 가집니다. 그러나 플랫폼은 합계가 맞지 않는 체크아웃을 자율적으로 완료해서는 안 됩니다(MUST NOT). 플랫폼은 체크아웃을 거부하거나, 에스컬레이션해서 continue_url로 구매자의 검토를 요청해야 합니다(SHOULD).

    각 최상위 항목에는 lines 배열이 있을 수 있습니다(MAY). 하위 라인은 최상위 항목과 같은 기본 형태(display_text와 amount)로, 상위 항목 아래에 항목별 내역을 제공합니다.
