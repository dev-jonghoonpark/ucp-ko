    체크아웃 기능¶

    • 기능 이름: dev.ucp.shopping.checkout

    개요¶

    플랫폼이 체크아웃 세션을 진행할 수 있게 합니다. AP2 위임(Mandate) 확장을 지원하지 않는 한, 체크아웃은 사용자가 신뢰할 수 있는 UI에서 직접 최종 확정해야 합니다.

    비즈니스는 계속 Merchant of Record(MoR)로 남으며, 이 기능으로 카드 결제를 받더라도 PCI DSS 인증을 받을 필요가 없습니다.

    흐름 개요¶

    결제¶

    결제 핸들러는 /.well-known/ucp에 있는 비즈니스의 UCP 프로필과 checkout.ucp.payment_handlers에서 찾을 수 있습니다. 핸들러는 결제 수단(예: Google Pay, Shop Pay)을 수집하는 처리 사양을 정의합니다. 구매자가 결제를 제출하면 플랫폼은 수집한 결제 수단 데이터로 payment.instruments 배열을 채웁니다.

    payment 객체는 체크아웃 생성 시 선택 사항입니다. 결제 처리가 필요 없는 사용 사례 (예: 견적 생성, 장바구니 관리)에서는 생략할 수 있습니다.

    풀필먼트¶

    UCP는 다양한 사용 사례를 수용하기 위해 풀필먼트를 확장으로 모델링합니다.

    체크아웃 객체에서 풀필먼트는 선택 사항입니다. 덕분에 플랫폼은 실물 상품에나 필요한 풀필먼트 세부 정보를 제공하지 않고도 디지털 상품을 체크아웃할 수 있습니다.

    체크아웃 상태 수명 주기¶

    체크아웃의 status 필드는 세션의 현재 단계를 나타내며, 다음에 어떤 조치가 필요한지 결정합니다. 상태는 비즈니스가 설정하고, 플랫폼은 진행에 필요한 사항을 알려 주는 메시지를 받습니다.

           +------------+                         +---------------------+
       | incomplete |<----------------------->| requires_escalation |
       +-----+------+                         |   (buyer handoff    |
             |                                |  via continue_url)  |
             | all info collected             +----------+----------+
             v                                           |
    +------------------+                                 |
    |ready_for_complete|                                 |
    |                  |                                 |
    | (platform can    |                                 | continue_url
    | call Complete    |                                 |
    |   Checkout)      |                                 |
    +--------+---------+                                 |
             |                                           |
             | Complete Checkout                         |
             v                                           |
   +--------------------+                                |
   |complete_in_progress|                                |
   +---------+----------+                                |
             |                                           |
             +-----------------------+-------------------+
                                     v
                               +-------------+
                               |  completed  |
                               +-------------+

                               +-------------+
                               |  canceled   |
                               +-------------+
          (session invalid/expired - can occur from any state)

    상태 값¶

    • incomplete: 체크아웃 세션에 필수 정보가 빠졌거나 해결해야 할 문제가 있습니다. 플랫폼은 messages 배열에서 맥락을 확인하고 Update Checkout으로 해결을 시도해야 합니다.

    • requires_escalation: 체크아웃 세션에 API로 제공할 수 없는 정보나 구매자의 입력이 필요합니다. 플랫폼은 무엇이 필요한지 파악하려면 messages를 확인해야 합니다(아래 에러 처리 참고). recoverable 에러가 있으면 먼저 해결합니다. 그런 다음 continue_url로 구매자에게 넘깁니다.

    • ready_for_complete: 체크아웃 세션에 필요한 정보가 모두 있어 플랫폼이 프로그래밍 방식으로 최종 확정할 수 있습니다. 플랫폼은 Complete Checkout을 호출할 수 있습니다.

    • complete_in_progress: 비즈니스가 Complete Checkout 요청을 처리하고 있습니다.

    • completed: 주문이 접수되었습니다.

    • canceled: 체크아웃 세션이 유효하지 않거나 만료되었습니다. 필요하면 플랫폼은 새 체크아웃 세션을 시작해야 합니다.

    에러 처리¶

    messages 배열에는 체크아웃 상태에 관한 에러, 경고, 정보 메시지가 담깁니다. ucp.status는 형태 판별자입니다. "success"는 응답에 기대한 페이로드가 담겨 있다는 뜻이고, "error"는 그 대신 에러 정보가 담겨 있다는 뜻입니다. 각 에러 메시지의 severity 필드는 권장 조치를 지정합니다.

    심각도 의미 플랫폼 조치
    recoverable 플랫폼이 API로 입력을 수정해 해결할 수 있음 리소스를 갱신하고 재시도
    requires_buyer_input 비즈니스가 API로 받을 수 없는 입력을 요구함 continue_url로 넘김
    requires_buyer_review 구매자의 검토와 승인이 필요함 continue_url로 넘김
    unrecoverable 작업 대상 리소스가 존재하지 않음 새 리소스나 입력으로 재시도하거나 continue_url로 넘김

    requires_* 심각도의 에러가 있으면 status: requires_escalation이 됩니다. 둘 다 구매자 넘김으로 이어지지만, 서로 다른 체크아웃 상태를 나타냅니다.

    • requires_buyer_input은 체크아웃이 미완료 상태라는 뜻입니다. 비즈니스가 API로 프로그래밍 방식 수집을 지원하지 않는 정보를 요구하는 경우입니다.
    • requires_buyer_review는 체크아웃은 완료 상태이지만, 정책, 규제, 권한 규칙상 주문 접수 전에 구매자의 승인이 필요하다는 뜻입니다(예: 고액 주문 승인, 첫 구매 정책).

    비즈니스가 새 리소스를 생성할 수 없거나 요청한 리소스가 더 이상 존재하지 않으면, 응답에는 실패를 설명하는 messages와 함께 ucp.status: "error"가 담기고 응답 본문에는 리소스가 포함되지 않습니다. 작업 대상 리소스가 없으면 메시지는 severity: "unrecoverable"을 사용해야 합니다(SHOULD). 예를 들어 비즈니스는 모든 상품을 구매할 수 없는 체크아웃 생성 요청을 거부할 수 있습니다.

    {
  "ucp": { "version": "2026-01-11", "status": "error" },
  "messages": [
    {
      "type": "error",
      "code": "out_of_stock",
      "content": "All requested items are currently out of stock",
      "severity": "unrecoverable"
    }
  ],
  "continue_url": "https://merchant.com/"
}

    REST 및 MCP 바인딩 예시를 참고하세요.

    에러 처리 알고리즘¶

    상태가 incomplete 또는 requires_escalation이면 플랫폼은 에러를 우선순위 스택으로 처리해야 합니다. 아래 예시는 세 가지 에러 유형, 즉 복구 가능한 에러(잘못된 전화번호), 구매자 입력 요구(배송 일정 지정), 검토 요구(고액 주문)가 있는 체크아웃입니다. 뒤의 두 가지는 넘김이 필요하며 플랫폼에 보내는 명시적 신호 역할을 합니다. 비즈니스는 이런 메시지를 가능한 한 일찍 노출해야 하며(SHOULD), 플랫폼은 넘김을 시작하기 전에 복구 가능한 에러부터 해결해야 합니다(SHOULD).

    {
  "status": "requires_escalation",
  "messages": [
    {
      "type": "error",
      "code": "invalid_phone",
      "severity": "recoverable",
      "content": "Phone number format is invalid"
    },
    {
      "type": "error",
      "code": "schedule_delivery",
      "severity": "requires_buyer_input",
      "content": "Select delivery window for your purchase"
    },
    {
      "type": "error",
      "code": "high_value_order",
      "severity": "requires_buyer_review",
      "content": "Orders over $500 require additional verification"
    }
  ]
}

    에러 처리 알고리즘 예시입니다.

    GIVEN response with messages array

FILTER errors FROM messages WHERE type = "error"

PARTITION errors INTO
  recoverable           WHERE severity = "recoverable"
  requires_buyer_input  WHERE severity = "requires_buyer_input"
  requires_buyer_review WHERE severity = "requires_buyer_review"
  unrecoverable         WHERE severity = "unrecoverable"

IF unrecoverable is not empty
  RETRY with new resource or inputs, or hand off via continue_url
  RETURN

IF recoverable is not empty
  FOR EACH error IN recoverable
    ATTEMPT to fix error (e.g., reformat phone number)
  CALL Update Checkout
  RETURN and re-evaluate response

IF requires_buyer_input is not empty
  handoff_context = "incomplete, additional input from buyer is required"
ELSE IF requires_buyer_review is not empty
  handoff_context = "ready for final review by the buyer"

    표준 에러¶

    표준 에러는 플랫폼이 일반적인 에러 처리 대신 구체적이고 적절한 UX로 처리해야 하는 표준화된 에러 코드입니다.

    코드 설명
    out_of_stock 특정 상품 또는 변형을 구매할 수 없음
    item_unavailable 상품을 구매할 수 없음(예: 판매 목록에서 제외됨)
    address_undeliverable 제공된 주소로 배송할 수 없음
    payment_failed 결제 처리에 실패함
    eligibility_invalid 완료 시점에 자격 주장을 검증할 수 없음

    비즈니스는 표준 에러에 severity: recoverable을 표시해야 합니다(SHOULD). 그러면 플랫폼은 일반적인 에러 메시지를 보여 주거나 체크아웃 완료 시점까지 미루지 않고 적절한 UX(품절 안내, 주소 확인 프롬프트, 결제 수단 변경)를 제공해야 한다는 것을 알 수 있습니다.

    예: out_of_stock은 미리 구체적인 UX가 필요하지만, payment_required는 제출 시점에 일반적인 방식으로 처리해도 됩니다.

    완료 시 자격 검증¶

    플랫폼은 context.eligibility로 구매자의 주장을 제공합니다. 로열티 멤버십, 결제 수단 혜택처럼 구매자가 자신이 받을 수 있다고 내세우는 혜택입니다. 이는 검증된 사실이 아니라 주장입니다. 비즈니스는 세션 중에 인식한 주장에 따라 조치할 수 있지만(MAY)(가격 조정, 상품 접근 허용, 잠정 할인 적용), 수락한 주장은 반드시 거래가 완료되기 전에 모두 해소해야 합니다(MUST).

    인식하지 못했거나 적용할 수 없는 주장 때문에 체크아웃이 막혀서는 안 됩니다(MUST NOT). 주장을 수락하지 않으면 비즈니스는 type: "warning" messages로 구매자에게 알려야 하며(SHOULD), 수락한 주장의 효과를 설명하는 데 type: "info"를 사용할 수 있습니다(MAY). 완료 시점까지 검증되지 않은 수락된 주장은 반드시 code: "eligibility_invalid"인 type: "error"로 처리해야 합니다(MUST)(아래 참고).

    자격 메시지 코드:

    유형 코드 발생 시점
    warning eligibility_not_accepted 주장을 인식하지 못했거나 적용할 수 없음
    info eligibility_accepted 수락된 주장의 효과
    error eligibility_invalid 완료 시점에 수락된 주장을 검증할 수 없음

    주장은 검증되거나 철회되면 해소됩니다.

    • 검증됨: 비즈니스가 완료 시점에 제공된 증명을 바탕으로 주장을 확인합니다. UCP는 검증 방식을 규정하지 않습니다. 증명은 결제 자격 증명, 신원 검증 기능, 또는 플랫폼과 비즈니스가 협상한 다른 메커니즘에서 올 수 있습니다.
    • 철회됨: 플랫폼이 완료 전에 context.eligibility에서 주장을 제거합니다(예: 구매자가 결제 수단을 바꾸거나 멤버십 주장을 철회한 경우). 주장이 제거되면 비즈니스는 그 주장 없이 다시 계산합니다.

    비즈니스는 해소되지 않은 자격 주장이 남은 상태로 거래를 완료해서는 안 됩니다(MUST NOT). 검증되지 않은 주장은 잘못된 가격 책정이나 제한된 상품에 대한 무단 접근으로 이어질 수 있습니다.

    검증에 실패한 경우:

    검증 실패는 반드시 messages 배열에만 영향을 주어야 합니다(MUST). 비즈니스는 반드시 code: "eligibility_invalid", severity: "recoverable"인 에러를 messages에 반환해야 합니다(MUST). 메시지는 path 필드로 어떤 주장을 검증할 수 없었는지 알려야 합니다(SHOULD). 그러면 플랫폼은 유효한 증명을 제공해 다시 제출하거나, 체크아웃을 재구성하거나(예: 자격이 없는 상품 제거, 주장 갱신), 시도를 포기할 수 있습니다(MAY).

    예를 들어 플랫폼이 context.eligibility로 스토어 카드 혜택을 주장하고, 비즈니스는 세션 동안 회원 가격을 적용합니다. 그런데 완료 시점에 결제 자격 증명이 주장한 결제 수단과 일치하지 않습니다.

    {
  "ucp": { "version": "2026-01-11", "status": "success" },
  "id": "checkout_abc",
  "status": "ready_for_complete",
  "line_items": [ "..." ],
  "totals": [ "..." ],
  "messages": [
    {
      "type": "error",
      "code": "eligibility_invalid",
      "severity": "recoverable",
      "content": "Payment credential does not match the claimed store card benefit.",
      "path": "$.context.eligibility[0]"
    }
  ]
}

    플랫폼은 구매자가 자격 요건을 충족하는 결제 수단으로 바꾸게 하거나, context.eligibility에서 주장을 제거해 체크아웃을 다시 협상한 다음(갱신된 가격, 재고 등을 받음) 완료를 다시 요청하는 방식으로 이 문제를 해결할 수 있습니다.

    경고 표시 방식¶

    경고 메시지의 presentation 필드는 플랫폼이 반드시 따라야 하는(MUST) 렌더링 계약을 지정합니다. 생략하면 기본값은 "notice"입니다.

    notice (기본값) disclosure
    내용 표시 MUST MUST
    path와의 근접 배치 MAY MUST
    닫기 허용 MAY MUST NOT
    image_url 렌더링 MAY MUST
    url 렌더링 MAY SHOULD
    준수할 수 없을 때 에스컬레이션 — continue_url로 MUST

    notice (기본값)¶

    경고의 기본 렌더링 계약입니다. 플랫폼은 반드시 경고 내용을 구매자에게 표시해야 합니다(MUST). 플랫폼은 알림을 배너, 트레이, 토스트 형태로 렌더링할 수 있으며(MAY), 구매자가 알림을 닫도록 허용할 수 있습니다(MAY).

    disclosure¶

    presentation: "disclosure"인 경고에는 안전 경고, 알레르기 유발 물질 표시, 규정 준수 내용처럼 반드시 아래 렌더링 계약을 따라야 하는(MUST) 고지가 담깁니다.

    플랫폼 요구 사항:

    • 반드시 경고 content를 구매자에게 표시해야 합니다(MUST).
    • 고지와 그 대상의 연관성이 유지되도록 반드시 path가 참조하는 구성 요소 가까이에 경고를 표시해야 합니다(MUST). path를 생략하면 고지는 응답 전체에 적용됩니다.
    • 경고를 숨기거나, 접거나, 자동으로 닫아서는 안 됩니다(MUST NOT).
    • image_url이 있으면 반드시 렌더링해야 합니다(MUST)(예: 경고 기호, 에너지 등급 라벨).
    • url이 있으면 이동 가능한 참조 링크로 렌더링해야 합니다(SHOULD).

    presentation: "disclosure"인 경고는 일반 알림보다 렌더링 우선순위가 높아야 합니다(SHOULD).

    고지 렌더링 계약을 지킬 수 없는 플랫폼은 슬그머니 일반 알림으로 낮춰 표시하지 말고, 반드시 continue_url로 판매자 UI에 에스컬레이션해야 합니다(MUST).

    비즈니스 요구 사항:

    • 경고 내용을 특정 구성 요소와 함께 표시해야 하고 숨기거나 자동으로 닫아서는 안 되는 경우, 반드시 presentation: "disclosure"를 설정해야 합니다(MUST).
    • path 필드로 고지를 응답의 관련 구성 요소와 연결해야 합니다(SHOULD).
    • 고지 범주를 식별하는 code(예: prop65, allergens, energy_label)를 제공해야 합니다(SHOULD).
    • 고지에 관련 시각 요소(예: 경고 기호, 에너지 등급 라벨)가 있으면 image_url을 제공해야 합니다(SHOULD).
    • 구매자가 더 자세히 알아볼 수 있는 참조 링크가 있으면 url을 제공해야 합니다(SHOULD).

    고지와 확인¶

    presentation 필드는 체크아웃을 진행할 수 있는지가 아니라 경고를 어떻게 렌더링할지를 제어합니다. 구매자의 명시적인 확인이나 승인도 필요하다면, 비즈니스는 적절한 구매자 입력을 확실히 받을 수 있도록 고지를 체크아웃 상태 수명 주기에 설명된 에스컬레이션 메커니즘과 함께 사용할 수 있습니다(MAY).

    관할권과 적용 범위¶

    특정 세션에 어떤 고지가 적용되는지 판단하고 관련 있는 고지만 반환하는 일은 비즈니스가 책임집니다. 비즈니스는 관할권별 요구 사항을 판단할 때 구매자가 제공한 데이터 (context 및 기타 입력)와 상품 속성을 사용해야 합니다(SHOULD). 플랫폼은 고지 적용 범위에 관여하거나 이를 결정하지 않고, 비즈니스에게서 받은 내용을 렌더링합니다.

    예시¶

    라인 아이템에 복구 가능한 에러와 고지 경고가 함께 담긴 체크아웃 응답입니다.

  "status": "incomplete",
  "currency": "USD",

    {
      "id": "li_1",
      "item": { "id": "item_456", "title": "Artisan Nut Butter Collection", "image_url": "https://merchant.com/nut-butter.jpg" },
      "quantity": 1,
      "totals": [{ "type": "subtotal", "amount": 1299 }]
    }
  ],
  "totals": [{ "type": "total", "amount": 1299 }],

      "type": "error",
      "code": "field_required",

    Continue URL¶

    continue_url 필드를 사용하면 플랫폼에서 비즈니스 UI로 체크아웃을 넘길 수 있으므로, 구매자가 체크아웃 세션을 이어서 진행하고 최종 확정할 수 있습니다.

    제공 조건¶

    비즈니스는 status = requires_escalation을 반환할 때 반드시 continue_url을 제공해야 합니다(MUST). 그 밖의 비종료 상태(incomplete, ready_for_complete, complete_in_progress)에서는 모두 continue_url을 제공해야 합니다(SHOULD). 종료 상태(completed, canceled)에서는 continue_url을 생략해야 합니다(SHOULD).

    형식¶

    continue_url은 반드시 절대 HTTPS URL이어야 하며(MUST), 매끄럽게 넘길 수 있도록 체크아웃 상태를 보존해야 합니다(SHOULD). 비즈니스는 다음 중 한 가지 방법으로 상태 보존을 구현할 수 있습니다(MAY).

    서버 측 상태(권장)¶

    서버 측 체크아웃 상태를 기반으로 하는 불투명한 URL입니다.

    https://business.example.com/checkout-sessions/{checkout_id}
    • 서버가 checkout_id에 연결된 체크아웃 상태를 유지합니다.
    • 단순하고 안전하며, 대부분의 구현에 권장합니다.
    • URL 수명은 보통 expires_at에 연동됩니다.

    체크아웃 퍼머링크¶

    체크아웃 상태를 직접 인코딩하여 서버 측 저장 없이도 재구성할 수 있는 상태 비저장 URL입니다. 비즈니스는 체크아웃 넘김과 빠른 진입을 돕기 위해 이 형식을 지원해야 합니다(SHOULD). 예를 들어 플랫폼은 바로 구매 흐름을 시작할 때 체크아웃 상태를 미리 채울 수 있습니다.

    참고: 체크아웃 퍼머링크는 REST 전송 방식 바인딩을 확장하는 REST 전용 구성 요소입니다. 퍼머링크에 접근하면 체크아웃 UI로 리디렉션되거나 체크아웃 페이지가 바로 렌더링됩니다.

    • 체크아웃 상태가 requires_escalation이면 반드시 continue_url을 사용해야 합니다(MUST).

    • 넘길 때는 플랫폼이 구성한 체크아웃 퍼머링크보다 비즈니스가 제공한 continue_url을 우선해야 합니다(SHOULD).

    • 정확한 에러 메시지를 제공해야 합니다(SHOULD).
    • 체크아웃 세션을 처리하는 로직은 반드시 결정론적이어야 합니다(MUST).
    • status = requires_escalation을 반환할 때 반드시 continue_url을 제공해야 합니다(MUST).
    • status = requires_escalation을 반환할 때 반드시 severity가 requires_buyer_input 또는 requires_buyer_review인 메시지를 하나 이상 포함해야 합니다(MUST).
    • 종료 상태가 아닌 모든 체크아웃 응답에 continue_url을 제공해야 합니다(SHOULD).
    • 체크아웃 세션이 "completed" 상태에 도달하면 변경할 수 없는 것으로 간주합니다.

    이름 타입 필수 설명

    id string Yes Unique identifier of the checkout session.
    line_items Array[Line Item Response] Yes List of line items being checked out.
    buyer Buyer No Representation of the buyer.

May be negative — the sign is intrinsic to the value (e.g., discounts are negative, charges are positive).

    렌더링 계약¶

    제시되는 합계의 내용과 순서에 대한 권한은 비즈니스에 있습니다. 올바른 표시 방식은 비즈니스가 지켜야 하는 지역, 상품, 규제 요구 사항(예: 다중 관할권 세금 항목화, 필수 수수료 고지)에 따라 달라지기 때문입니다.

    플랫폼은 반드시 모든 최상위 항목을 제공된 순서대로 렌더링해야 합니다(MUST).

    for entry in totals:
    render_line(entry.display_text, entry.amount)

    플랫폼은 하위 라인을 보조 세부 정보로 렌더링할 수 있습니다(MAY).

    for entry in totals:
    render_line(entry.display_text, entry.amount)
    if entry.lines:
        for sub in entry.lines:
            render_detail_line(sub.display_text, sub.amount)

    플랫폼은 항목을 해석, 필터링, 재정렬, 집계하거나 자체 표시 로직을 적용해서는 안 됩니다(MUST NOT).

    totals[]의 불변 조건은 다음과 같습니다.

    • 모든 항목에는 type과 amount가 있습니다. 플랫폼은 display_text가 제공되면 이를 사용해야 합니다(SHOULD). well-known 유형에는 대체용 기본 표시 라벨이 있습니다(아래 표 참고). 알 수 없는 유형은 반드시 display_text를 포함해야 합니다(MUST).
    • 금액은 부호 있는 정수입니다. 음수 값은 차감(예: 할인), 양수 값은 가산을 뜻합니다. 부호가 곧 방향입니다.
    • type: "subtotal"은 반드시 정확히 하나 있어야 합니다(MUST).
    • type: "total"은 반드시 정확히 하나 있어야 합니다(MUST).

    검증¶

    플랫폼은 비즈니스의 값을 자체 계산한 합계로 바꿔서는 안 됩니다(MUST NOT). 플랫폼은 제공된 합계를 검증할 수 있습니다(MAY).

    assert sum(e.amount for e in totals if e.type != "total") == total_entry.amount

    계산한 합이 type: "total" 항목과 맞지 않더라도 플랫폼은 렌더링 결과를 바꿔서는 안 됩니다(MUST NOT). 표시에서는 비즈니스가 제시한 합계가 권위를 가집니다. 그러나 플랫폼은 합계가 맞지 않는 체크아웃을 자율적으로 완료해서는 안 됩니다(MUST NOT). 플랫폼은 체크아웃을 거부하거나, 에스컬레이션해서 continue_url로 구매자의 검토를 요청해야 합니다(SHOULD).

    Well-Known 유형¶

    유형 부호 기본 라벨 의미
    subtotal + Subtotal 라인 아이템 가격의 합
    discount − Discount 주문 또는 라인 아이템 수준 할인
    items_discount − Item Discounts 라인 아이템 할인의 합산
    fulfillment + Shipping 배송, 배달, 픽업 요금
    tax + Tax 세금
    fee + Fee 수수료 및 추가 요금
    total = Total 권위 있는 최종 합계(정확히 하나)

    display_text가 제공되면 플랫폼은 반드시 이를 사용해야 합니다(MUST). well-known 유형에서 생략되었다면 플랫폼은 위의 기본 라벨을 사용해야 합니다(SHOULD). well-known 유형의 부호 규칙은 스키마가 강제합니다. 차감 유형(discount, items_discount)은 반드시 음수 금액이어야 하고(MUST), 가산 유형(subtotal, fulfillment, tax, fee)은 반드시 음수가 아닌 금액이어야 합니다(MUST).

    type 필드는 개방형 문자열이므로 비즈니스는 well-known 집합에 없는 값도 사용할 수 있습니다(MAY). 알 수 없는 유형은 반드시 display_text를 포함해야 하며(MUST)(스키마가 강제함), 금액의 부호가 의미를 나타냅니다.

    반복 유형¶

    subtotal과 total을 제외한 모든 유형은 여러 번 나타날 수 있습니다(MAY). 다중 관할권 세금 라인이나 항목별 수수료가 그 예입니다.

    하위 라인(lines)¶

    각 최상위 항목에는 lines 배열이 있을 수 있습니다(MAY). 하위 라인은 최상위 항목과 같은 기본 형태(display_text와 amount)로, 상위 항목 아래에 항목별 내역을 제공합니다.

    불변 조건: sum(lines[].amount)는 반드시 상위 항목의 amount와 같아야 합니다(MUST).

    반드시 렌더링해야 하는 것(MUST, 최상위 항목)과 선택적으로 노출할 수 있는 것(MAY, 하위 라인)은 비즈니스가 결정합니다. 플랫폼은 하위 라인이 제공되면 렌더링해야 합니다(SHOULD).
