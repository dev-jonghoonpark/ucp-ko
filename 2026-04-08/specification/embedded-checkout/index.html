    체크아웃 기능 - EP 바인딩¶

    소개¶

    임베디드 체크아웃 프로토콜(Embedded Checkout Protocol, ECP)은 UCP 임베디드 프로토콜(Embedded Protocol, EP) 전송 바인딩을 체크아웃용으로 구현한 것입니다. ECP를 사용하면 호스트가 비즈니스의 체크아웃 인터페이스를 임베드하고, 구매자가 체크아웃과 상호작용할 때 이벤트를 받으며, 주소·결제 수단 선택 같은 주요 사용자 동작을 위임받을 수 있습니다. ECP는 (REST처럼) 전송 바인딩입니다. 즉 어떤 데이터가 있는지가 아니라 어떻게 통신하는지를 정의합니다.

    W3C Payment Request와의 개념적 대응¶

    ECP는 W3C Payment Request API에서 착안해, 그 멘탈 모델을 임베디드 체크아웃 시나리오에 맞게 조정했습니다. Payment Request에 익숙한 개발자라면 비슷한 패턴을 알아볼 수 있지만, 실행 모델은 다릅니다.

    W3C Payment Request: 브라우저가 제어합니다. 비즈니스가 show()를 호출하면 브라우저가 네이티브 결제 시트를 렌더링합니다. 이벤트는 결제 핸들러에서 비즈니스로 흐릅니다.

    임베디드 체크아웃: 비즈니스가 제어합니다. 호스트는 비즈니스의 체크아웃 UI를 iframe/webview에 임베드합니다. 이벤트는 양방향으로 흐르며, 호스트는 선택적으로 위임을 받아 특정 상호작용을 네이티브로 처리할 수 있습니다.

    개념 W3C Payment Request 임베디드 체크아웃
    초기화 new PaymentRequest() continue_url로 임베디드 컨텍스트 로드
    UI 준비 show()가 Promise 반환 ec.start 알림
    결제 수단 변경 paymentmethodchange 이벤트 ec.payment.change 알림
    주소 변경 shippingaddresschange 이벤트 ec.fulfillment.change 및 ec.fulfillment.address_change_request
    결제 제출 사용자 수락 → PaymentResponse 위임된 ec.payment.credential_request
    완료 response.complete() ec.complete 알림
    에러/메시지 Promise 거부 ec.messages.change 알림

    핵심 차이: W3C Payment Request에서는 브라우저가 결제 흐름을 조율합니다. 임베디드 체크아웃에서는 비즈니스가 임베디드 컨텍스트 안에서 흐름을 조율하며, 네이티브 경험을 위해 특정 UI(결제 수단 선택, 주소 선택기)를 선택적으로 호스트에 위임합니다.

    용어 및 행위자¶

    커머스 역할¶

    • 비즈니스: 상품/서비스와 체크아웃 경험을 제공하는 판매 주체.
    • 구매자: 구매를 하는 최종 사용자.

    기술 구성 요소¶

    • 호스트(Host): 체크아웃을 임베드하는 애플리케이션(예: AI 에이전트 앱, 슈퍼 앱, 브라우저). 결제 핸들러와 사용자 인증을 담당합니다.
    • 임베디드 체크아웃(Embedded Checkout): iframe이나 webview에 렌더링되는 비즈니스의 체크아웃 인터페이스. 체크아웃 흐름과 주문 생성을 담당합니다.
    • 결제 핸들러(Payment Handler): 사용자 인증(생체 인식/PIN)과 자격 증명 발급을 수행하는 보안 구성 요소.

    요구 사항¶

    디스커버리¶

    ECP 지원 여부는 두 단계로 알립니다. 서비스 수준 디스커버리는 지원 능력을 선언하고, 체크아웃 응답은 실제 사용 가능 여부와 세션별로 허용된 설정을 확정합니다.

    서비스 수준 디스커버리¶

    비즈니스는 /.well-known/ucp 프로필에 embedded 전송 방식을 넣어 임베디드 체크아웃 프로토콜 지원을 선언합니다.

    서비스 디스커버리 예시:

    {
    "services": {
        "dev.ucp.shopping": [
            {
                "version": "2026-04-08",
                "transport": "rest",
                "schema": "https://ucp.dev/2026-04-08/services/shopping/rest.openapi.json",
                "endpoint": "https://merchant.example.com/ucp/v1"
            },
            {
                "version": "2026-04-08",
                "transport": "mcp",
                "schema": "https://ucp.dev/2026-04-08/services/shopping/mcp.openrpc.json",
                "endpoint": "https://merchant.example.com/ucp/mcp"
            },
            {
                "version": "2026-04-08",
                "transport": "embedded",
                "schema": "https://ucp.dev/2026-04-08/services/shopping/embedded.openrpc.json"
            }
        ]
    }
}

    서비스 정의에 embedded가 없으면 비즈니스는 continue_url을 이용한 리디렉션 기반 체크아웃 이어가기만 지원합니다.

    체크아웃별 설정¶

    서비스 수준 디스커버리는 비즈니스가 ECP를 지원한다고 선언할 뿐, 모든 체크아웃 세션에서 ECP가 활성화된다고 보장하지는 않습니다. 비즈니스는 특정 세션의 ECP 사용 가능 여부와 허용된 위임을 나타내기 위해 반드시 체크아웃 응답에 config.delegate가 포함된 임베디드 서비스 바인딩을 넣어야 합니다(MUST).

    체크아웃 응답 예시:

    {
    "id": "checkout_abc123",
    "status": "open",
    "continue_url": "https://merchant.example.com/checkout/abc123",
    "ucp": {
        "version": "2026-04-08",
        "services": {
            "dev.ucp.shopping": [
                {
                    "version": "2026-04-08",
                    "transport": "embedded",
                    "config": {
                        "delegate": ["payment.credential", "fulfillment.address_change", "window.open"]
                    }
                }
            ]
        },
        "capabilities": {...},
        "payment_handlers": {...}
    }
}

    config.delegate 배열은 이 체크아웃 세션에서 비즈니스가 수락한 위임, 즉 호스트가 ec_delegate로 요청한 것과 비즈니스가 허용하는 것의 교집합을 확정합니다. 이 값은 다음에 따라 달라질 수 있습니다.

    • 장바구니 내용: 일부 상품은 비즈니스가 직접 처리하는 결제 흐름이 필요할 수 있습니다
    • 에이전트 권한: 인증된 에이전트는 더 많은 위임을 받을 수 있습니다
    • 비즈니스 정책: 위험 규칙, 지역 제한 등

    config.delegate가 포함된 임베디드 서비스 바인딩이 있으면 다음을 뜻합니다.

    • 이 체크아웃은 continue_url로 ECP를 사용할 수 있습니다
    • config.delegate는 비즈니스가 수락한 위임을 확정합니다
    • 이는 ec.ready 핸드셰이크의 delegate 필드와 대응합니다

    체크아웃 응답에 임베디드 서비스 바인딩이 없으면 (서비스 수준 디스커버리에서 임베디드 지원을 선언했더라도) 그 체크아웃은 continue_url을 이용한 리디렉션 기반 이어가기만 지원합니다.

    임베디드 체크아웃 URL 로드¶

    임베디드 서비스 바인딩이 포함된 체크아웃 응답을 받은 호스트는 임베디드 컨텍스트에서 continue_url을 로드해 ECP 세션을 시작할 수 있습니다(MAY).

    임베디드 컨텍스트를 로드하기 전에 호스트는 다음을 해야 합니다(SHOULD).

    1. config.delegate에서 사용 가능한 위임을 확인합니다
    2. 호스트가 지원하려는 위임의 핸들러를 준비합니다
    3. 비즈니스가 요구하면 선택적으로 인증 자격 증명을 준비합니다

    세션을 시작하려면 호스트는 반드시 continue_url에 ec_ 접두사가 붙은 ECP 쿼리 파라미터를 덧붙여야 합니다(MUST).

    다양한 임베딩 환경에서 최대한 호환되도록 모든 ECP 파라미터는 HTTP 헤더가 아닌 URL 쿼리 문자열로 전달합니다. 네임스페이스 오염을 피하고 비즈니스 고유 쿼리 파라미터와 ECP 파라미터를 명확히 구분하기 위해 파라미터에는 ec_ 접두사를 붙입니다.

    • ec_version (string, REQUIRED): 이 세션의 UCP 버전 (형식: YYYY-MM-DD). 체크아웃 응답의 버전과 일치해야 합니다. 버전은 세션 초기화 시 협상되며 반드시 ECP 세션이 유지되는 동안 변하지 않아야 합니다(MUST). 핸드셰이크 이후에는 어느 쪽도 버전을 바꿀 수 없습니다.
    • ec_auth (string, OPTIONAL): 비즈니스가 정의한 형식의 인증 토큰
    • ec_delegate (string, OPTIONAL): 호스트가 처리하려는 위임을 쉼표로 구분한 목록. 임베디드 서비스 바인딩의 config.delegate의 부분집합이어야 합니다(SHOULD).
    • ec_color_scheme (string, OPTIONAL): 체크아웃 UI의 색 구성표 선호값. 유효한 값: light, dark. 제공되지 않으면 임베디드 체크아웃은 시스템 설정을 따릅니다.

    인증¶

    토큰 형식:

    • auth 파라미터 형식은 전적으로 비즈니스가 정의합니다
    • 일반적인 형식으로는 JWT, OAuth 토큰, API 키, 세션 식별자 등이 있습니다
    • 비즈니스는 반드시 기대하는 토큰 형식과 검증 절차를 문서화해야 합니다(MUST)

    예시(참고용 - JWT 기반):

    // One possible implementation using JWT
{
  "alg": "HS256",
  "typ": "JWT"
}
{
  "iat": 1234567890,
  "exp": 1234568190,
  "jti": "unique-id",
  // ... business-specific claims ...
}

    비즈니스는 반드시 자체 보안 요구 사항에 따라 인증을 검증해야 합니다(MUST).

    인증을 포함한 초기화 예시:

    https://example.com/checkout/abc123?ec_version=2026-01-11&ec_auth=eyJ...

    참고: 모든 쿼리 파라미터 값은 RFC 3986에 따라 올바르게 URL 인코딩해야 합니다.

    위임¶

    선택 파라미터 ec_delegate는 구매자가 임베디드 체크아웃 UI에서 처리하는 대신 호스트가 네이티브로 처리하려는 오퍼레이션을 선언합니다. 각 위임 식별자는 일관된 패턴 ec.{delegation}_request를 따르는 대응 _request 메시지에 매핑됩니다.

    위임 식별자 예시:

    ec_delegate 값 대응 메시지
    payment.instruments_change ec.payment.instruments_change_request
    payment.credential ec.payment.credential_request
    fulfillment.address_change ec.fulfillment.address_change_request
    window.open ec.window.open_request

    확장은 자체 위임 식별자를 정의합니다. 사용 가능한 옵션은 각 확장의 명세를 참고하세요.

    ?ec_version=2026-01-11&ec_delegate=payment.instruments_change,payment.credential,fulfillment.address_change,window.open

    색 구성표¶

    선택 파라미터 ec_color_scheme을 사용하면 호스트가 임베디드 체크아웃이 쓸 색 구성표를 지정할 수 있어, 호스트 애플리케이션과 체크아웃 UI의 시각적 일관성을 맞출 수 있습니다.

    유효한 값:

    값 설명
    light 밝은 색 구성표 사용(밝은 배경, 어두운 텍스트)
    dark 어두운 색 구성표 사용(어두운 배경, 밝은 텍스트)

    기본 동작:

    ec_color_scheme이 제공되지 않으면 임베디드 체크아웃은 prefers-color-scheme 미디어 쿼리나 Sec-CH-Prefers-Color-Scheme HTTP 클라이언트 힌트로 구매자의 시스템 설정을 사용할 수 있으며, 변경을 감지해 그에 맞게 갱신해야 합니다(SHOULD).

    구현 참고 사항:

    • 기본적으로 임베디드 체크아웃은 구매자의 시스템 색 구성표 설정을 따르고, 변경을 감지해 그에 맞게 갱신해야 합니다(SHOULD)
    • ec_color_scheme이 명시적으로 제공되면 반드시 시스템 설정보다 우선하고, 로드 즉시 적용되며, 세션이 유지되는 동안 계속 적용되어야 합니다(MUST).
    • 비즈니스는 지원하지 않는 값을 무시할 수 있습니다(MAY)

    예시:

    https://example.com/checkout/abc123?ec_version=2026-01-11&ec_color_scheme=dark

    위임 협상¶

    위임은 비즈니스 정책에서 최종 수락까지 범위가 점점 좁아지는 연쇄를 따릅니다.

    config.delegate ⊇ ec_delegate ⊇ ec.ready delegate
    1. 비즈니스 허용(체크아웃 응답의 config.delegate): 이 체크아웃 세션에서 비즈니스가 허용하는 위임 집합
    2. 호스트 요청(ec_delegate URL 파라미터): 호스트가 네이티브로 처리하려는 부분집합
    3. ECP 수락(ec.ready의 delegate): 임베디드 체크아웃이 실제로 위임할 최종 부분집합

    각 단계는 이전 단계의 부분집합입니다.

    • 호스트는 config.delegate에 있는 위임만 요청해야 합니다(SHOULD)
    • 비즈니스는 config.delegate에 없는 위임을 수락하지 않아야 하며(SHOULD NOT), 반드시 수락한 위임을 ec.ready에서 확정해야 합니다(MUST)

    위임 계약¶

    위임은 호스트와 임베디드 체크아웃 사이에 구속력 있는 계약을 만듭니다. 다만 임베디드 체크아웃은 비즈니스 정책에 따라 인증되었거나 승인된 호스트에만 위임을 허용할 수 있습니다(MAY).

    위임 수락¶

    임베디드 체크아웃은 다음을 근거로 어떤 위임을 받아들일지 결정합니다.

    • 인증 상태(ec_auth 파라미터)
    • 호스트 권한 수준
    • 비즈니스 정책

    임베디드 체크아웃은 반드시 ec.ready 요청의 delegate 필드로 수락한 위임을 표시해야 합니다(MUST)(ec.ready 참고). 요청된 위임을 수락하지 않으면 임베디드 체크아웃은 반드시 해당 동작을 자체 UI로 처리해야 합니다(MUST).

    구속 요건¶

    위임이 수락되면 양측은 구속력 있는 계약을 맺습니다.

    임베디드 체크아웃의 책임:

    1. 해당 동작이 트리거되면 반드시 적절한 {action}_request 메시지를 보내야 합니다(MUST)
    2. 진행하기 전에 반드시 호스트의 응답을 기다려야 합니다(MUST)
    3. 위임된 동작에 대해 자체 UI를 보여서는 안 됩니다(MUST NOT)

    호스트의 책임:

    1. 받은 모든 {action}_request 메시지에 반드시 응답해야 합니다(MUST)
    2. 사용자가 취소하면 반드시 적절한 에러로 응답해야 합니다(MUST)
    3. 위임을 처리하는 동안 로딩/처리 중 상태를 보여 주어야 합니다(SHOULD)

    3.3.3 위임 흐름¶

    1. 요청: 임베디드 체크아웃이 현재 상태를 담아 ec.{domain}.{action}_request 메시지를 보냅니다(id 포함)
    2. 네이티브 UI: 호스트가 위임된 동작에 대한 네이티브 UI를 표시합니다
    3. 응답: 호스트가 일치하는 id와 result 또는 error를 담은 JSON-RPC 응답을 돌려보냅니다
    4. 갱신: 임베디드 체크아웃이 상태를 갱신하고, 이어서 변경 알림을 보낼 수 있습니다

    도메인별 위임 세부 사항은 결제 확장, 풀필먼트 확장, 윈도 확장을 참고하세요.

    탐색 제약¶

    체크아웃이 임베디드 모드로 렌더링될 때 구현은 체크아웃에 집중된 경험을 유지하기 위해 체크아웃 밖으로의 탐색을 막아야 합니다(SHOULD). 임베디드 뷰는 범용 브라우저가 아니라 체크아웃 흐름을 제공하기 위한 것입니다.

    탐색 요건:

    • 임베디드 체크아웃은 체크아웃 흐름 밖의 URL로 이동하려는 시도를 차단하거나 가로채야 합니다(SHOULD)
    • 임베디드 체크아웃은 체크아웃을 벗어나게 하는 UI 요소(예: 외부 링크, 내비게이션 바)를 제거하거나 비활성화해야 합니다(SHOULD)
    • 임베드하는 쪽은 컨테이너 수준에서 추가 탐색 제한을 구현할 수 있습니다(MAY)

    허용되는 예외: 체크아웃 완료에 필요한 경우 다음 탐색 시나리오는 허용할 수 있습니다(MAY).

    • 결제 제공자 리디렉션: 외부 사이트 결제 흐름
    • 3D Secure 인증: 카드 인증 프레임과 리디렉션
    • 은행 승인: 오픈 뱅킹 또는 유사한 승인 흐름
    • 신원 확인: 필요한 경우 KYC/AML 규정 준수 확인

    이러한 예외 흐름은 완료되면 사용자를 체크아웃 흐름으로 되돌려야 합니다(SHOULD).

    전송 및 메시징¶

    ECP는 EP 공통 전송 계층을 사용합니다. 메시지 형식, 메시지 유형, 응답 처리 규칙은 임베디드 프로토콜 — 전송 및 메시징을 참고하세요.

    모든 응답의 ucp.version은 반드시 세션 초기화 시 협상되고 호스트가 ec.ready 응답에서 확정한 ec_version을 그대로 반환해야 합니다(MUST). 버전은 세션에 묶여 있으며, ECP 세션이 유지되는 동안 바뀌어서는 안 됩니다(MUST NOT).

    통신 채널¶

    ECP는 EP 공통 통신 채널 모델을 따릅니다. 일반적인 패턴은 임베디드 프로토콜 — 통신 채널을 참고하세요.

    네이티브 호스트의 경우 체크아웃 전용 전역 객체는 다음과 같습니다.

    • window.EmbeddedCheckoutProtocolConsumer(권장)
    • window.webkit.messageHandlers.EmbeddedCheckoutProtocolConsumer
    • window.EmbeddedCheckoutProtocol(호스트 → 임베디드 체크아웃)

    메시지 범주¶

    핵심 메시지¶

    핵심 메시지는 ECP 명세에서 정의하며, 모든 구현은 반드시 이를 지원해야 합니다(MUST). 모든 메시지는 임베디드 체크아웃에서 호스트로 전송됩니다.

    범주 목적 패턴 핵심 메시지
    핸드셰이크 호스트와 임베디드 체크아웃 사이의 연결 수립 요청 ec.ready
    인증 임베디드 체크아웃과 호스트 사이의 인증 데이터 교환 요청 ec.auth
    수명 주기 체크아웃 상태 전환 알림 알림 ec.start, ec.complete
    상태 변경 체크아웃 필드 변경 알림 알림 ec.line_items.change, ec.buyer.change, ec.payment.change, ec.messages.change, ec.totals.change
    세션 에러 체크아웃 리소스와 무관한 세션 수준 에러 신호 알림 ec.error

    확장 메시지¶

    확장은 추가 메시지를 정의해 임베디드 프로토콜을 확장할 수 있습니다(MAY). 확장 메시지는 반드시 다음 명명 규칙을 따라야 합니다(MUST).

    • 알림: ec.{domain}.change — 상태 변경 알림(id 없음)
    • 위임 요청: ec.{domain}.{action}_request — 응답이 필요함(id 있음)

    여기서:

    • {domain}은 디스커버리의 도메인 식별자와 일치합니다(예: payment, fulfillment, window)
    • {action}은 위임되는 구체적인 동작을 나타냅니다(예: instruments_change, address_change)
    • _request 접미사는 응답이 필요한 위임 지점임을 나타냅니다

    핸드셰이크 메시지¶

    ec.ready¶

    렌더링되면 임베디드 체크아웃은 반드시 ec.ready 메시지로 부모 컨텍스트에 준비 완료를 알려야 합니다(MUST). 이 메시지는 호스트와 임베디드 체크아웃 사이의 보안 통신 채널을 초기화하고, 어떤 위임이 수락되었는지와 추가 인증 교환이 필요한지를 전달하며, UCP 체크아웃 동작으로 전달되지 않은 표시 전용 체크아웃 상태를 호스트가 추가로 제공할 수 있게 합니다.

    • 방향: 임베디드 체크아웃 → 호스트
    • 유형: 요청
    • 페이로드:
      • delegate (array of strings, REQUIRED): 임베디드 체크아웃이 수락한 위임 식별자 목록. 반드시 ec_delegate(호스트가 요청한 것)와 체크아웃 응답의 config.delegate(비즈니스가 허용하는 것) 모두의 부분집합이어야 합니다(MUST). 빈 배열은 수락된 위임이 없다는 뜻입니다.
      • auth (object, OPTIONAL): 추가 고려 사항 때문에 ec_auth URL 파라미터로 충분하지 않거나 적용할 수 없을 때, 비즈니스는 이 객체 안에 type 문자열을 지정해 최초 핸드셰이크 중에 인증을 요청할 수 있습니다. 이 type 문자열 값은 ec.auth에 포함되는 페이로드 내용과 대응합니다.

    메시지 예시(수락된 위임 없음):

    {
    "jsonrpc": "2.0",
    "id": "ready_1",
    "method": "ec.ready",
    "params": {
        "delegate": [],
        "auth": {
            "type": "oauth"
        }
    }
}

    메시지 예시(위임 수락됨):

    {
    "jsonrpc": "2.0",
    "id": "ready_1",
    "method": "ec.ready",
    "params": {
        "delegate": ["payment.credential", "fulfillment.address_change", "window.open"],
        "auth": {
            "type": "oauth"
        }
    }
}

    ec.ready 메시지는 요청이므로, 호스트는 핸드셰이크를 완료하기 위해 반드시 응답해야 합니다(MUST).

    • 방향: 호스트 → 임베디드 체크아웃
    • 유형: 응답
    • 결과 페이로드:
      • ucp (object, REQUIRED): UCP 프로토콜 메타데이터. version은 협상된 ec_version을 확정하며, status는 반드시 "success"여야 합니다(MUST). 이 버전은 세션에 묶여 있습니다. 호스트가 여기서 프로토콜 버전을 명시적으로 확정하며, 세션이 유지되는 동안 바뀌어서는 안 됩니다(MUST NOT).
      • upgrade (object, OPTIONAL): 임베디드 체크아웃이 호스트와 통신하는 데 쓰는 통신 채널을 어떻게 갱신할지 기술하는 객체. 이 필드가 있으면 호스트는 credential을 포함해서는 안 됩니다(MUST NOT). 채널이 다시 수립되므로 여기서 보낸 자격 증명은 폐기됩니다.
      • credential (string, OPTIONAL): 요청된 인증 데이터로, OAuth 토큰, JWT, API 키 등의 형태일 수 있습니다. 요청에 auth가 있으면 반드시 설정해야 합니다(MUST). upgrade가 있으면 설정해서는 안 됩니다(MUST NOT).
      • checkout (object, OPTIONAL): UCP 체크아웃 동작으로 전달되지 않은 표시 전용 추가 체크아웃 상태. 체크아웃 UI를 채우는 데 쓰이며, 특정 조건에서 다음 필드를 채우는 용도로만 사용할 수 있습니다.
        • payment.instruments: 호스트와 임베디드 체크아웃이 모두 payment.instruments_change 위임을 수락한 경우 덮어쓸 수 있습니다.

    메시지 예시:

    {
    "jsonrpc": "2.0",
    "id": "ready_1",
    "result": {
        "ucp": { "version": "2026-04-08", "status": "success" },
        "credential": "fake_identity_linking_oauth_token"
    }
}

    ec.error¶

    ec.error는 EP 공통 세션 에러 패턴을 구현합니다. 페이로드 명세와 호스트 처리 요건은 임베디드 프로토콜 — 세션 에러를 참고하세요.

    결제 확장¶

    결제 확장은 호스트가 상태 변경 알림과 위임 요청을 사용해 사용자 에스컬레이션 흐름을 조율하는 방법을 정의합니다. 체크아웃 URL에 ec_delegate=payment.instruments_change,payment.credential이 포함되면 호스트가 결제 수단 선택과 토큰 획득을 제어하게 되며, 그 결과로 임베디드 체크아웃에 상태 갱신을 제공합니다.

    결제 개요 및 호스트 선택¶

    결제 위임에서는 호스트와 임베디드 체크아웃을 조율하는 두 가지 패턴을 쓸 수 있습니다.

    옵션 A: 호스트가 임베디드 체크아웃에 맡김 호스트는 URL에 결제 위임을 포함하지 않습니다. 임베디드 체크아웃이 자체 UI와 결제 흐름으로 결제 수단 선택과 처리를 담당합니다. 이것이 위임하지 않는 표준 흐름입니다.

    옵션 B: 호스트가 제어 호스트는 체크아웃 URL에 ec_delegate=payment.instruments_change,payment.credential을 포함해, 결제 UI와 토큰 획득을 호스트에 위임하라고 임베디드 체크아웃에 알립니다. 위임된 경우:

    • 임베디드 체크아웃의 책임:
      • 현재 결제 수단을 변경 진입점(예: "결제 수단 변경" 버튼)과 함께 표시합니다
      • 결제를 제출하기 전에 ec.payment.credential_request 메시지에 대한 응답을 기다립니다
    • 호스트의 책임:
      • ec.payment.instruments_change_request에 응답해 구매자가 다른 결제 수단을 선택할 수 있는 네이티브 UI를 렌더링하고, 선택된 수단으로 응답합니다
      • ec.payment.credential_request에 응답해 선택된 결제 수단의 결제 토큰을 획득하고, 그 토큰을 임베디드 체크아웃에 보냅니다

    풀필먼트 확장¶

    풀필먼트 확장은 호스트가 주소 선택을 위임받아 네이티브 주소 선택기 경험을 제공하는 방법을 정의합니다. 체크아웃 URL에 ec_delegate=fulfillment.address_change가 포함되면 호스트가 배송 주소 선택을 제어하게 되며, 그 결과로 임베디드 체크아웃에 주소 갱신을 제공합니다.

    풀필먼트 개요 및 호스트 선택¶

    풀필먼트 위임에서는 두 가지 패턴을 쓸 수 있습니다.

    옵션 A: 호스트가 임베디드 체크아웃에 맡김 호스트는 URL에 풀필먼트 위임을 포함하지 않습니다. 임베디드 체크아웃이 자체 UI와 주소 입력 양식으로 주소 입력을 처리합니다. 이것이 위임하지 않는 표준 흐름입니다.

    옵션 B: 호스트가 제어 호스트는 체크아웃 URL에 ec_delegate=fulfillment.address_change를 포함해, 주소 선택 UI를 호스트에 위임하라고 임베디드 체크아웃에 알립니다. 위임된 경우:

    임베디드 체크아웃의 책임:

    • 현재 배송 주소를 변경 진입점(예: "주소 변경" 버튼)과 함께 표시합니다
    • 구매자가 주소 변경을 시작하면 ec.fulfillment.address_change_request를 보냅니다
    • 호스트가 반환한 주소를 바탕으로 배송 옵션을 갱신합니다

    호스트의 책임:

    • ec.fulfillment.address_change_request에 응답해 구매자가 배송 주소를 선택하거나 입력할 수 있는 네이티브 UI를 렌더링합니다
    • 선택된 주소를 UCP PostalAddress 형식으로 응답합니다

    주소 형식¶

    우편 주소¶

    이름 타입 필수 설명
    extended_address string 아니요 아파트 호수, C/O, 대체 이름 같은 주소 보충 정보.
    street_address string 아니요 도로명 주소.
    address_locality string 아니요 도로명 주소가 속하고 해당 지역 안에 있는 시·군·구. 예: Mountain View.
    address_region string 아니요 시·군·구가 속하고 해당 국가 안에 있는 지역. 해당하는 국가에서는 필수입니다(예: 미국의 주, 캐나다의 주). 예: California 또는 그 밖의 적절한 1차 행정 구역.
    address_country string 아니요 국가. 2자리 ISO 3166-1 alpha-2 형식(예: "US")을 권장합니다. 하위 호환성을 위해 "SGP" 같은 3자리 ISO 3166-1 alpha-3 국가 코드나 "Singapore" 같은 전체 국가명도 사용할 수 있습니다.
    postal_code string 아니요 우편번호. 예: 94043.
    first_name string 아니요 선택 사항. 주소와 연결된 연락처의 이름.
    last_name string 아니요 선택 사항. 주소와 연결된 연락처의 성.
    phone_number string 아니요 선택 사항. 주소와 연결된 연락처의 전화번호.

    윈도 확장¶

    윈도 확장은 구매자가 비즈니스가 제시한 링크를 활성화했을 때 임베디드 체크아웃이 호스트에 알리는 방법을 정의합니다. 체크아웃 URL에 ec_delegate=window.open이 포함되면 호스트는 반드시 모든 ec.window.open_request를 처리하고 요청을 확인 응답해야 합니다(MUST).

    이는 임베디드 체크아웃이 관련 없는 페이지로의 탐색을 막기 위해 무조건 적용하는 탐색 제약과는 별개입니다.

    윈도 개요 및 호스트 선택¶

    윈도 위임에서는 두 가지 패턴을 쓸 수 있습니다.

    옵션 A: 호스트가 임베디드 체크아웃에 맡김 호스트는 ec_delegate에 window.open을 포함하지 않습니다. 임베디드 체크아웃이 자체 인라인 UI로 링크 표시를 처리합니다. 이것이 위임하지 않는 표준 흐름입니다.

    옵션 B: 호스트가 제어 호스트는 체크아웃 URL에 ec_delegate=window.open을 포함해, 구매자가 링크를 활성화하면 ec.window.open_request를 보내라고 임베디드 체크아웃에 알립니다. 위임된 경우:

    임베디드 체크아웃의 책임:

    • 구매자가 비즈니스가 제시한 링크를 활성화하면 반드시 ec.window.open_request를 보내야 합니다(MUST)

    호스트의 책임:

    • 요청된 URL이 https 스킴을 쓰는지 반드시 검증해야 합니다(MUST)
    • 추가 호스트 보안 정책(예: 출처 검증)을 적용해야 합니다(SHOULD)
    • 승인한 모든 요청에 대해 반드시 콘텐츠를 구매자에게 보여 주어야 합니다(MUST) (예: 모달, 새 탭 등)
    • 요청을 처리했으면 JSON-RPC 성공 결과로, 호스트 정책 때문에 탐색을 막았으면 window_open_rejected_error 에러로 반드시 응답해야 합니다(MUST)
    • 요청이 거부되었으면 구매자에게 알릴 수 있습니다(MAY)

    window.open 위임을 수락하면 호스트는 구매자의 링크 상호작용을 처리할 책임을 집니다. 임베디드 체크아웃은 해당 링크에 대해 자체 UI를 표시해서는 안 됩니다(MUST NOT).

    ec.window.open_request 페이로드에는 URL만 담깁니다. 더 풍부한 맥락(예: 링크 유형이나 레이블)이 필요한 호스트는 요청된 URL을 체크아웃 세션의 checkout.links 배열과 대조해 추가 메타데이터를 얻을 수 있습니다(MAY).

    보안 및 에러 처리¶

    에러 코드¶

    공통 에러 코드는 임베디드 프로토콜 — 에러 코드를 참고하세요. 임베디드 체크아웃은 위임 관련 시나리오를 위해 다음 코드를 추가로 정의합니다.

    코드 심각도 설명
    not_allowed_error recoverable 요청에 유효한 사용자 활성화(User Activation)가 없었습니다(원치 않는 결제 요청 방지 참고).
    window_open_rejected_error unrecoverable 호스트 정책 때문에 탐색이 막혔습니다. 호스트는 구매자에게 요청이 거부되었음을 알릴 수 있습니다(MAY).

    not_allowed_error에서 복구하려면 위임을 다시 시도하기 전에 새로운 사용자 활성화 제스처가 필요합니다.

    웹 기반 호스트의 보안¶

    ECP는 CSP, iframe 샌드박싱, credentialless iframe, 엄격한 출처 검증에 관한 EP 공통 보안 요건을 그대로 따릅니다. 전체 명세는 임베디드 프로토콜 — 보안을 참고하세요.

    원치 않는 결제 요청 방지¶

    취약점: 악의적이거나 침해된 비즈니스가 사용자 상호작용 없이 프로그래밍 방식으로 ec.payment.credential_request를 트리거할 수 있습니다.

    완화책(호스트 제어 실행): 이 위험을 없애기 위해 호스트를 결제 실행의 유일한 신뢰 개시자로 지정합니다. 호스트는 토큰을 내주기 전에 사용자 확인 UI를 표시해야 합니다(SHOULD). 트리거가 임베디드 체크아웃에서 시작된 경우 사용자 모르게 토큰화하는 것은 엄격히 금지됩니다(PROHIBITED).

    line_items Array[Line Item Response] 예 체크아웃 중인 라인 아이템 목록.
    buyer Buyer 아니요 구매자 정보.
    context Context 아니요 관련성 판단과 현지화를 위한 잠정적 구매자 신호로, 권위 있는 데이터가 아닙니다. 검증된 입력(예: 배송 주소)이 없으면 비즈니스는 이 값을 사용해야 하며(SHOULD), 더 신뢰도 높은 신호(인증된 계정, 위험 탐지)나 규제 제약(수출 통제)과 맞지 않으면 무시하거나 우선순위를 낮출 수 있습니다(MAY). 자격 판단과 정책 적용은 반드시 체크아웃 시점에 구속력 있는 거래 데이터로 수행해야 합니다(MUST). 컨텍스트는 개인을 식별할 수 없어야 하며(SHOULD), 단계적으로 공개할 수 있습니다. 초기에는 대략적인 신호를, 세션이 진행되면서 더 세밀한 정보를 제공합니다. 더 세밀한 데이터(배송 주소, 청구 주소)가 컨텍스트보다 우선합니다.
    signals Signals 아니요 승인과 악용 방지를 돕기 위해 플랫폼이 제공하는 환경 데이터. 값은 구매자가 주장한 내용이어서는 안 됩니다(MUST NOT). 플랫폼은 직접 관찰했거나 독립적으로 검증 가능한 제3자 증명에 근거한 신호를 제공합니다. 여러 확장이 공유 네임스페이스에 값을 추가할 때 출처를 보장하고 충돌을 막기 위해, 모든 신호 키는 반드시 역도메인 이름을 사용해야 합니다(MUST).
    attribution Attribution 아니요 플랫폼이 내보내는 추천 및 전환 이벤트 맥락: 캠페인 식별자, 클릭 ID, source/medium 마커 등. 브라우저 기반 흐름에서 플랫폼이 URL 쿼리 매개변수로 전달하는 것과 같은 매개변수입니다.
    status string 예 현재 단계와 필요한 조치를 나타내는 체크아웃 상태. 상태 전이에 대한 자세한 내용은 체크아웃 상태 수명 주기 문서를 참고하세요.
    허용 값: incomplete, requires_escalation, ready_for_complete, complete_in_progress, completed, canceled
    currency string 예 판매자가 판단한 시장을 반영하는 ISO 4217 통화 코드. 주소, 컨텍스트, geo IP로 결정합니다. 구매자는 신호를 제공하고 통화는 판매자가 결정합니다.
    totals Totals 예 장바구니의 각종 합계.
    messages Array[Message] 아니요 체크아웃 세션 상태에 대한 오류·정보 메시지 목록.
    links Array[Link] 예 플랫폼이 표시할 링크(개인정보처리방침, 이용약관). 법적 준수를 위해 필수입니다.
    expires_at string 아니요 RFC 3339 만료 타임스탬프입니다. 보내지 않으면 기본 TTL은 생성 시점부터 6시간입니다.
    continue_url string 아니요 체크아웃 핸드오프와 세션 복구용 URL. status가 requires_escalation이면 반드시 제공해야 합니다(MUST). 형식과 가용성 요구 사항은 명세를 참고하세요.
    payment Payment 아니요 핸들러를 포함한 결제 구성.
    order Order Confirmation 아니요 이 체크아웃 세션으로 생성된 주문의 세부 정보.

    주문¶

    체크아웃이 성공적으로 완료되면 반환되는 객체로, 확인 세부 정보를 담습니다.

    이름 타입 필수 설명
    ucp any 예 주문 응답용 UCP 메타데이터. 구매 후에는 결제 핸들러가 필요 없습니다.
    id string 예 고유 주문 식별자.
    label string 아니요 주문을 식별하기 위한 사람이 읽을 수 있는 라벨. 반드시 비즈니스만 제공해야 합니다(MUST).
    checkout_id string 예 정산 대사를 위한 연관 체크아웃 ID.
    permalink_url string 예 판매자 사이트에서 주문에 접근하는 퍼머링크.
    line_items Array[Order Line Item] 예 구매한 항목을 나타내는 라인 아이템. 주문 후 수정이나 교환으로 바뀔 수 있습니다.
    fulfillment object 예 풀필먼트 데이터: 구매자 예상 정보와 실제로 일어난 일.
    adjustments Array[Adjustment] 아니요 풀필먼트와 독립적으로 존재하는 주문 후 이벤트(환불, 반품, 크레딧, 분쟁, 취소 등).
    currency string 예 ISO 4217 통화 코드. 반드시 원래 체크아웃 세션의 통화와 일치해야 합니다(MUST).
    totals Totals 예 주문의 각종 합계.
    messages Array[Message] 아니요 비즈니스 결과 메시지(오류, 경고, 정보). 비즈니스가 플랫폼에 상태나 문제를 전달해야 할 때 포함됩니다.
    attribution Attribution 아니요 원래 체크아웃과 연결된 어트리뷰션의 스냅샷입니다. 주문에서는 읽기 전용입니다.

    결제¶

    이름 타입 필수 설명
    instruments Array[Payment Instrument Selected Payment Instrument] 아니요 이 결제에 사용할 수 있는 결제 수단. 각 결제 수단은 handler_id 필드로 특정 핸들러와 연결됩니다. 핸들러는 기본 payment_instrument 스키마를 확장해 핸들러별 필드를 추가할 수 있습니다.

    결제 수단¶

    구매자가 사용할 수 있는 특정 결제 방법(예: 특정 신용카드, 은행 계좌, 지갑 자격 증명)을 나타냅니다.

    이름 타입 필수 설명
    id string 예 플랫폼이 할당하는, 이 결제 수단 인스턴스의 고유 식별자.
    handler_id string 예 이 결제 수단을 생성한 핸들러 인스턴스의 고유 식별자. 결제 핸들러 정의의 'id' 필드에 해당합니다.
    type string 예 결제 수단의 대분류(예: 'card', 'tokenized_card'). 구체적인 스키마에서 이 값을 상수로 제한합니다.
    billing_address Postal Address 아니요 이 결제 방법에 연결된 청구지 주소.
    credential Payment Credential 아니요 모든 결제 자격 증명의 기본 정의. 구체적인 자격 증명 유형은 핸들러가 정의합니다.
    display object 아니요 이 결제 수단의 표시 정보. 각 결제 수단 스키마가 결제 핸들러의 설명에 따라 고유한 표시 속성을 정의합니다.

    결제 핸들러¶

    특정 결제 수단의 인증과 처리를 담당하는 처리자 또는 지갑 제공자(예: Google Pay, Stripe, 은행 앱)를 나타냅니다.

    응답에 포함되는 핸들러 참조. 핸들러를 런타임에 사용하기 위한 전체 구성 상태를 포함할 수 있습니다.

    이름 타입 필수 설명
    version string 예 YYYY-MM-DD 형식의 엔티티 버전.
    spec string 아니요 사람이 읽을 수 있는 명세 문서의 URL.
    schema string 아니요 이 엔터티의 구조와 페이로드를 정의하는 JSON Schema의 URL.
    id string 예 이 엔터티 인스턴스의 고유 식별자. 인스턴스가 여러 개일 때 구분하는 데 사용합니다.
    config object 아니요 엔티티별 구성. 구조는 각 엔티티의 스키마가 정의합니다.
    available_instruments Array[object] 아니요 이 핸들러가 지원하는 결제 수단 유형과 선택적 제약 조건. 없으면 모든 결제 수단을 사용 가능한 것으로 간주합니다.
